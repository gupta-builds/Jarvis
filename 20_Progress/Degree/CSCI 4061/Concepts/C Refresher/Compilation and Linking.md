# Compilation and Linking
## One-Line Answer
==Turning a `.c` file into a runnable program is four separate, inspectable stages - preprocessor, compiler, assembler, linker - and nearly every confusing build error is really a complaint from exactly one of those four stages, not a vague "it didn't compile."==
## Mechanism
*Inputs/state:* one or more `.c` source files, their `#include`d headers, and (for anything beyond a single file) a set of already-compiled `.o` object files or `.a`/`.so` libraries to link against.
*Causal sequence (`gcc source.c -o program` run end to end, per CSAPP Ch. 7):*
1. **Preprocessor** expands every `#include` by literally pasting the named header's text in place, expands `#define` macros, and strips comments - the output is still C source, just with every header's declarations physically inlined. `gcc -E source.c` shows this stage's raw output directly.
2. **Compiler** translates that expanded C source into assembly for the target architecture - `gcc -S source.c` stops here and leaves a human-readable `source.s` file. HW05/HW06 use exactly this flag to compare hand-written C against its compiler-generated assembly line by line.
3. **Assembler** turns that assembly text into machine code, bundled into an **object file** (`source.o`) - real binary instructions, but not yet a runnable program, because any function or variable the file references but doesn't define (like `printf` or `cos`) is left as an unresolved symbol reference, a placeholder waiting to be filled in.
4. **Linker** resolves those placeholders: it walks every `.o` file and every library being linked against, matches each unresolved symbol to the place that actually defines it, and merges everything into one final executable (or reports failure if a symbol is never found anywhere).
*Where libraries enter:* a library is just a pre-built bundle of `.o` files the linker searches during stage 4 instead of compiling from source. **Static libraries** (`.a`, built with `ar`) get their needed object code *physically copied into* the final executable at link time - the executable is self-contained but larger, and `nm` on the result shows the library's function definitions baked directly in. **Dynamic/shared libraries** (`.so`, built with `gcc -shared`) are the opposite: the linker only records *that* the program needs the library and leaves the actual code location to be resolved at **load time**, when the OS loader maps the `.so`'s code into the process's address space - `ldd a.out` lists exactly which shared libraries a given executable still depends on at startup. HW12's `ds_search_dynamic/Makefile` shows the real commands: `gcc -fpic -c tree.c` (compile each source file to position-independent object code), then `gcc -shared -o libds_search.so tree.o array.o list.o` (bundle those objects into one shared object). The concrete payoff HW12 demonstrates: `libds_search.so` bundles three *independent* backend implementations of the same search interface - a binary search tree (`tree.c`), a linear array scan (`array.c`), and a linked list (`list.c`) - behind one shared library name, so a caller program can be relinked against a different backend without recompiling its own source at all.
*The `-I`/`-L`/`-l` flags, worked from a real failure:* compiling `do_search.c` bare fails immediately at the *preprocessor* stage - `fatal error: ds_search.h: No such file or directory` - because the header lives in a different directory than the source file. `-I ds_search_static` tells the preprocessor an extra directory to search for `#include "..."` headers, fixing that specific error. Compiling again then fails at the *linker* stage instead, with undefined-reference errors for the search functions themselves, because the compiler can see the function prototypes (from the header) but not their actual code. `-L ds_search_static` tells the *linker* an extra directory to search for library files, and `-lds_search` names the specific library to link (`libds_search.a`/`.so`, with the `lib` prefix and extension both dropped in the flag) - only with both the `-I` (preprocessor) and `-L`/`-l` (linker) flags together does the build actually succeed, because they fix two genuinely different stages' worth of missing information.
*Output:* a linked executable (static-library case) or a linked executable plus a runtime dependency on one or more `.so` files the OS loader must find at launch (dynamic case) - `LD_LIBRARY_PATH` is the environment variable that tells the loader extra directories to search for those `.so` files, exactly the same kind of "extra search path" idea as `-L` but applied at run time instead of link time.
*Complexity/limitation:* a dynamic library saves disk space and memory across many programs sharing one copy, and lets a bug fix in the library reach every program using it without recompiling them - at the cost of a program that fails at *launch*, not compile time, if the right `.so` can't be found on the target machine.
## Contrast / What It Is Not
- **Compile-time vs. link-time vs. load-time errors are not interchangeable** - a missing header is a preprocessor-stage failure (`fatal error: ... No such file or directory`), a missing function definition is a linker-stage failure (`undefined reference to ...`), and a missing shared library at program startup is a load-time failure (`error while loading shared libraries`) - each needs a different flag (`-I`, `-L`/`-l`, or a fixed `LD_LIBRARY_PATH`/library install) to actually fix, so diagnosing which stage failed is the real first step, not guessing.
- **Static vs. dynamic linking** is not "old vs. new" - static libraries are simpler to reason about and produce a fully self-contained binary; dynamic libraries are smaller per-executable and allow shared, swappable, patchable code, which is exactly why HW12 builds the same search functionality both ways to make the tradeoff concrete.
## Failure Modes / Misconceptions
> [!WARNING]
> Treating "it didn't compile" as one error category. `gcc do_math.c` failing with complaints about `cos`/`pow` is a *linker* error (the math library `libm` was never linked, fixed with `-lm`), not a syntax error in the source - the fix is a build flag, not a code change, and reading the exact wording ("undefined reference" vs. "No such file or directory" vs. "cannot open shared object file") tells you which of the four stages actually failed.
> [!WARNING]
> Forgetting a shared library's runtime dependency. A program linked with `-lds_search` against a `.so` compiles and links successfully, but running it without the `.so` findable (via `LD_LIBRARY_PATH` or a system install path) fails at launch with a "cannot open shared object file" error - this is a genuinely different failure, at a genuinely different stage, than any build-time error, which is exactly what HW12 Problem 3(B) demonstrates directly.
> [!WARNING]
> Multiple-inclusion of the same header across a multi-file build, when a header lacks an include guard (`#ifndef HEADER_H` / `#define HEADER_H` / `#endif`) or `#pragma once`. Because the preprocessor's job is literal text-pasting, a header included twice (directly or through two other headers that both include it) redefines every struct/function it declares twice, which the compiler stage then rejects as a redefinition error - the fix is always an include guard, not reordering `#include` lines.

## Flashcards
#cards/csci2021
What are the four stages between a `.c` file and a runnable executable, in order?::Preprocessor (expands `#include`/`#define`, strips comments) → compiler (C source to assembly) → assembler (assembly to machine code in a `.o` object file) → linker (resolves every unresolved symbol reference and merges object code/libraries into one executable).
`gcc do_search.c` fails with `fatal error: ds_search.h: No such file or directory`. Which build stage failed, and which flag fixes it?::The preprocessor stage - it couldn't find the header named in `#include "ds_search.h"`. Fix with `-I <directory>`, which tells the preprocessor an extra directory to search for included headers.
After adding `-I`, the same build now fails with undefined-reference errors for search functions. Which stage is failing now, and why didn't `-I` fix it?::The linker stage. `-I` only fixed the preprocessor's ability to find the header (so the compiler now knows the function prototypes); the linker still has no idea where the actual function *definitions* live until `-L <directory> -l<libname>` points it at the library.
What is the real mechanical difference between a static (`.a`) and a dynamic (`.so`) library at the moment a program using it actually runs?::A static library's needed object code was physically copied into the executable at link time, so nothing external is needed at runtime. A dynamic library's code is only loaded into the process's address space when the OS loader runs the program, so the `.so` file must still be findable at that moment, or the program fails to launch even though it linked successfully.
Why does HW12's `ds_search_dynamic` library being built from three separate backend files (`tree.c`, `array.c`, `list.c`) matter as an example, rather than being incidental?::It demonstrates the actual point of a shared library: a caller program written against one interface (`ds_search.h`) can be relinked against a different backend implementation without recompiling the caller's own source at all - the backend is swappable precisely because it's resolved outside the caller's own compiled code.
Why does a header without an include guard cause a compile error in a multi-file build, even though the header itself has no bugs?::The preprocessor pastes a header's text in literally, every time it's `#include`d. If the same header gets included twice (directly or via two other headers that both include it), every struct and function it declares gets pasted - and therefore redefined - twice, which the compiler then rejects.
