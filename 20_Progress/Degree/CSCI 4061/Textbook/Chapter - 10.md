### 10.1 Introduction
A **signal** is a software interrupt providing an asynchronous notification delivered by the operating system to a process when an event occurs (p. 313).
In contrast to a hardware **interrupt** (a hardware-generated notification to the CPU), a signal is a software-level notification delivered to a recipient process that interrupts normal execution at any arbitrary instruction (Lec05).
==Signals are asynchronous events that can arrive at random times during execution, interrupting whatever instruction stream the recipient process was running.==
### 10.2 Signal Concepts
Every signal has a symbolic name starting with `SIG` defined as positive integer constants in `<signal.h>` (p. 313–314).
Signal number 0 is defined as the **null signal**, which carries no signal condition but is used by `kill` for permission and process existence checks (p. 314).
*Signal Generation Conditions:* Signals are generated by terminal keys (e.g., interrupt key Ctrl-C, quit key Ctrl-\, suspend key Ctrl-Z), hardware exceptions (e.g., divide by zero, invalid memory reference), the `kill` system call or command, or software conditions (e.g., timer expiration, writing to a readerless pipe) (p. 314).
*Signal Dispositions:* A process can respond to a signal in one of three ways, known as the **disposition** or action associated with the signal (p. 315):
1. Ignore the signal (all signals can be ignored except **SIGKILL** and **SIGSTOP**) (p. 315).
2. Catch the signal by registering a custom **signal handler** function (p. 315).
3. Allow the default action to apply (typically process termination, termination with a **core file**, ignoring, pausing, or resuming execution) (p. 315).
*Core File Generation:* Core dumps write a memory image to disk for debugging unless restricted by set-user-ID permissions, write permissions, or resource limits (`RLIMIT_CORE`) (p. 315–317).
*Numbered Signal Table (Lec05 / `kill -L`):* Although programmers should always use symbolic names from `<signal.h>` rather than hardcoded numbers, standard system mappings include (Lec05):
- 2: **SIGINT** (Terminal Interrupt / Ctrl-C; default action: Terminate) (p. 316, 319; Lec05).
- 8: **SIGFPE** (Arithmetic Exception / Divide by 0; default action: Terminate with core) (p. 316, 318; Lec05).
- 9: SIGKILL (Kill / Termination; default action: Terminate; cannot be caught or ignored) (p. 316, 319; Lec05).
- 15: **SIGTERM** (Software Termination; default action: Terminate; default signal sent by `kill` command) (p. 316, 321; Lec05).
- 17: **SIGCHLD** (Child Process Status Change; default action: Ignore) (p. 316, 317; Lec05).
- 18: **SIGCONT** (Continue Stopped Process; default action: Resume execution) (p. 316, 317; Lec05).
- 19: SIGSTOP (Stop Process; default action: Pause execution; cannot be caught or ignored) (p. 316, 320; Lec05).
*Custom User Signals:* **SIGUSR1** and **SIGUSR2** are two distinct signal names explicitly reserved for application-defined custom use (p. 322; Lec05).
*Other Standard Signals:* **SIGABRT** (abnormal termination via `abort`), **SIGALRM** (timer expiration), **SIGBUS** (hardware/memory alignment fault), **SIGHUP** (terminal hangup/session leader disconnect; used by daemons to reload configuration files), **SIGILL** (illegal instruction), **SIGINFO** (BSD status request Ctrl-T), **SIGIOT** (hardware fault / abort), **SIGPIPE** (write to pipe/socket with no reader), **SIGQUIT** (terminal quit key Ctrl-\ generating core dump), **SIGSEGV** (invalid memory reference / segmentation violation), **SIGSYS** (invalid system call), **SIGTSTP** (interactive terminal stop key Ctrl-Z), **SIGTTIN** (background read from controlling terminal), **SIGTTOU** (background write to controlling terminal), **SIGURG** (urgent out-of-band socket data), and **SIGWINCH** (terminal window size change) (p. 317–322).
*Signal Lifecycle:* The lifecycle of a signal progresses through four states (p. 335; Lec05):
1. Event Occurs & Signal Generated: A hardware or software event generates a signal for a target process (p. 335; Lec05).
2. **Pending**: A signal is generated but not yet delivered while the target process waits for CPU execution time or while the signal is blocked (p. 335; Lec05).
3. **Delivered**: The kernel takes the designated action for the signal when the process executes (p. 335; Lec05).
4. Disposition Executed: The process terminates, pauses, ignores, or executes a caught handler (p. 315, 335; Lec05).
*Pending-Signal Coalescing:* Standard UNIX signals do not queue; if a second instance of an already-pending signal type is generated before the first is delivered, the second instance is silently dropped (p. 336; Lec05). Consequently, when a signal handler executes, there is no way to determine how many times that signal actually fired (Lec05).
*Job Control & Shell Execution (Lab 02):* Shell job control manages background and stopped jobs using explicit commands (Lab 02):
- `jobs`: Lists backgrounded or stopped jobs in the current shell session (Lab 02).
- `fg %1`: Brings job 1 to the foreground and sends `SIGCONT` to resume execution (Lab 02).
- `bg %1`: Resumes job 1 in the background (Lab 02).
- `kill %1`: Sends `SIGTERM` to job 1 by default (Lab 02).
*print_nums Execution Demo (Lab 02):* Running `while (1) { printf("%d\n", i++); sleep(1); }`:
- Ctrl-C sends `SIGINT`, terminating the process immediately (Lab 02).
- Ctrl-Z sends `SIGTSTP`, pausing the process and causing the shell to report "Stopped" (Lab 02).
- Running `fg %1` sends `SIGCONT`, resuming process execution and counting from the exact interrupted state (Lab 02).
### 10.3 signal Function
*Function Prototypes (`<signal.h>`):*
```c
void (*signal(int signo, void (*func)(int)))(int);
```

Or simplified using `typedef` (p. 323–324):

```
typedef void Sigfunc(int);
Sigfunc *signal(int, Sigfunc *);
```

Returns previous signal disposition on success, or `SIG_ERR` on error (p. 323). _Special Constant Values (`<signal.h>`):_

- `SIG_ERR`: `(void (*)())-1` (p. 325).
- `SIG_DFL`: `(void (*)())0` (sets action to default) (p. 323, 325).
- `SIG_IGN`: `(void (*)())1` (ignores the signal) (p. 323, 325). _Implementation Differences & Portability:_ The `signal` function is defined by ISO C without multiprocess semantics; early System V implementations provided unreliable signal semantics, whereas BSD implemented `signal` using **sigaction** (p. 323). Modern POSIX programs should use `sigaction` instead of `signal` due to implementation non-portability (p. 323; Lec05). Furthermore, `signal` cannot inspect a signal's disposition without altering it (p. 326). _Example Code (Catching SIGUSR1 and SIGUSR2):_

```
#include "apue.h"

static void sig_usr(int);

int main(void) {
    if (signal(SIGUSR1, sig_usr) == SIG_ERR)
        err_sys("can't catch SIGUSR1");
    if (signal(SIGUSR2, sig_usr) == SIG_ERR)
        err_sys("can't catch SIGUSR2");
    for ( ; ; )
        pause();
}

static void sig_usr(int signo) {
    if (signo == SIGUSR1)
        printf("received SIGUSR1\n");
    else if (signo == SIGUSR2)
        printf("received SIGUSR2\n");
    else
        err_dump("received signal %d\n", signo);
}
```

_Program Start-Up & exec Semantics:_ When a program calls `exec`, the dispositions of all caught signals are reset to `SIG_DFL` because the new memory image no longer contains the signal handler function addresses; ignored signals (`SIG_IGN`) remain ignored across `exec` (p. 325). Non-job-control shells automatically set background commands (`cc main.c &`) to ignore `SIGINT` and `SIGQUIT` so terminal interrupts do not kill background jobs (p. 325). _Process Creation & fork Semantics:_ When a process calls `fork`, the child inherits all signal dispositions from the parent because the child begins as an exact copy of the parent's address space where handler addresses remain valid (p. 326).

### 10.9 kill and raise Functions

_Function Prototypes (`<signal.h>`):_

```
int kill(pid_t pid, int signo);
int raise(int signo);
```

Both return 0 on success, or -1 on error (p. 337). Equivalence: Calling **raise**`(signo)` is exactly equivalent to calling `kill(getpid(), signo)` (p. 337). _Misnomer Note:_ The name `kill` is a historical misnomer; the function sends a signal to a process or process group, which may terminate, pause, ignore, or catch the signal depending on its disposition (p. 325; Lec05). _pid Conditions for kill:_

- `pid > 0`: Signal is sent to the specific process whose process ID is `pid` (p. 337).
- `pid == 0`: Signal is sent to all processes whose process group ID equals that of the sender (excluding system processes like `swapper` and `init`) (p. 337).
- `pid < 0`: Signal is sent to all processes whose process group ID equals `|pid|` for which the sender has permission (p. 337).
- `pid == -1`: Broadcast signal sent to all processes on the system for which the sender has permission to send signals (p. 337). _Null Signal (`signo == 0`):_ Passing a signal number of 0 tests whether a specific process or process group exists and whether the caller has permission to send signals to it without actually delivering a signal (p. 337). If the target process does not exist, `kill` returns -1 with `errno` set to `ESRCH` (p. 337). Note that this existence check is non-atomic (p. 338). _Permissions:_ To send a signal, the calling process must be the superuser (`root`) or its real or effective user ID must match the recipient's real or effective user ID (p. 314, 337). _Self-Delivery Timing:_ If `kill` generates an unblocked signal for the calling process itself, `signo` or another pending unblocked signal is delivered to the process before `kill` returns (p. 338). _Shell Command Syntax:_ In a shell terminal session, signals are sent using `kill -s TERM 1234` or `kill -9 1234` (Lec05).
### 10.5 Interrupted System Calls
If a process catches a signal while blocked in a "slow" system call, the system call is interrupted, returning an error of -1 with **errno** set to `EINTR` (p. 327).
*Slow vs. Fast System Calls:* System calls fall into two categories: "slow" system calls that can block forever (including **read** or **write** on pipes, terminals, and network devices; **open** on FIFOs or terminal devices; **pause**; **wait** and **waitpid**; and certain **ioctl** operations) and all other system calls (fast system calls and disk I/O operations, which return quickly unless a hardware error occurs) (p. 328).
*Tricky Item 1 (System Calls & Retry Loops):* Before automatic system call restarting, an interrupted slow system call returned -1 with `errno == EINTR`, forcing programmers to write manual retry loops (p. 328–329; Lec06):
```c
do {
    ret = read(STDIN_FILENO, buf, BUFSIZE);
} while (ret == -1 && errno == EINTR);
```

Modern POSIX systems eliminate manual retry loops by setting the `SA_RESTART` flag when installing signal handlers with **sigaction**, instructing the kernel to restart interrupted system calls automatically upon handler return (p. 329; Lec06).

### 10.6 Reentrant Functions

A function is **reentrant** (or **async-signal safe**) if it can be safely entered by a signal handler while a previous call to the same function is currently in progress in main-line execution (p. 330; Lec06). _Tricky Item 3 (Non-Reentrant Functions):_ Functions are non-reentrant if they use static internal data structures, allocate or free heap memory via **malloc** or **free**, or belong to the C standard I/O library (`FILE *` streams) (p. 330–331; Lec06). Explicitly named non-reentrant functions unsafe for signal handlers include **printf**, `malloc`, `free`, **strtok**, and **getpwnam** (p. 330–331; Lec06). Calling a non-reentrant function inside a signal handler while main-line code is executing that function corrupts internal data structures (such as `malloc`'s heap linked list), resulting in unpredictable behavior or segmentation faults (`SIGSEGV`) (p. 331–332; Lec06). _Tricky Item 2 (errno Corruption & Fix):_ Because `errno` is a single global (or thread-local) variable, a signal handler invoking a function that modifies `errno` (such as **stat** or `wait`) will overwrite the `errno` value set by a recently interrupted main-line system call before main-line code can inspect it or call **perror** (p. 330–331; Lec06). To prevent `errno` corruption, signal handlers that invoke functions modifying `errno` must save `errno` at handler entry and restore it before returning (p. 331; Lec06):

```
void my_handler(int signo) {
    int errno_save = errno;
    /* handler execution */
    errno = errno_save;
}
```

### 10.11 Signal Sets

A **signal set** is represented by the primitive data type **sigset_t**, holding a bitmask collection of multiple signal types (p. 344; Lec05). _Signal Set Manipulation Functions (`<signal.h>`):_

- **sigemptyset**`(sigset_t *set)`: Initializes `set` to exclude all signal types; returns 0 on success or -1 on error (p. 344; Lec05). Must be called for every new signal set before use (p. 344).
- **sigfillset**`(sigset_t *set)`: Initializes `set` to include all possible signal types; returns 0 on success or -1 on error (p. 344; Lec05).
- **sigaddset**`(sigset_t *set, int signo)`: Adds signal `signo` to `set`; returns 0 on success or -1 on error (p. 344; Lec05).
- **sigdelset**`(sigset_t *set, int signo)`: Removes signal `signo` from `set`; returns 0 on success or -1 on error (p. 344; Lec05).
- **sigismember**`(const sigset_t *set, int signo)`: Tests whether `signo` is contained in `set`; returns 1 if true, 0 if false, or -1 on error (p. 344; Lec05).

### 10.12 sigprocmask Function

Each process maintains a **process mask** defining the set of signals currently blocked from delivery (p. 346; Lec05). _Function Prototype (`<signal.h>`):_

```
int sigprocmask(int how, const sigset_t *restrict set, sigset_t *restrict oset);
```

Returns 0 on success, or -1 on error (p. 346). _how Operation Arguments:_

- `SIG_BLOCK`: Unions `set` with the current signal mask to block additional signals (p. 346; Lec05).
- `SIG_UNBLOCK`: Intersects the current mask with the complement of `set` to unblock signals (p. 346; Lec05).
- `SIG_SETMASK`: Replaces the current process mask entirely with `set` (p. 346; Lec05). _Mask Inspection & Unblockable Signals:_ Passing `set == NULL` returns the current signal mask in `oset` without modifying process block settings (p. 346; Lec05). `SIGKILL` and `SIGSTOP` cannot be blocked; system attempts to block them are silently ignored or rejected (p. 346; Lec05). _Critical Section Pattern:_ Processes protect critical regions of code from signal interruption by blocking target signals before entering the region and restoring the original mask upon completion (p. 359; Lec05):

```
sigset_t newmask, oldmask;
sigemptyset(&newmask);
sigaddset(&newmask, SIGINT);
if (sigprocmask(SIG_BLOCK, &newmask, &oldmask) < 0)
    perror("sigprocmask");
/* critical section of code */
if (sigprocmask(SIG_SETMASK, &oldmask, NULL) < 0)
    perror("sigprocmask");
```

### 10.13 sigpending Function

_Function Prototype (`<signal.h>`):_

```
int sigpending(sigset_t *set);
```

Returns 0 on success, or -1 on error (p. 347). _Semantics:_ Populates `set` with the collection of signals that are currently blocked from delivery and pending for the calling process (p. 347). Allows processes to inspect signals generated during blocked execution before unblocking them (p. 347–348).

### 10.14 sigaction Function

The **signal** function is considered deprecated and bad practice due to platform-dependent unreliable semantics; modern POSIX applications must use `sigaction` because it provides standardized, reliable signal handling that eliminates entire categories of race conditions (p. 323, 349–350; Lec06). _Function Prototype (`<signal.h>`):_

```
int sigaction(int signo, const struct sigaction *restrict act, struct sigaction *restrict oact);
```

Returns 0 on success, or -1 on error (p. 350; Lec06). Modifies or inspects the action for signal `signo` using configuration structure `act`, returning previous settings in `oact` if non-null (p. 350; Lec06). _struct sigaction Fields (`<signal.h>`):_

- `void (*sa_handler)(int)`: Pointer to a signal handler function accepting a single integer argument and returning void, or built-in disposition constants **SIG_DFL** (default action) or **SIG_IGN** (ignore signal) (p. 350; Lec06).
- `sigset_t sa_mask`: Set of signals automatically added to the process signal mask while the handler function is executing, preventing recursive signal interruption during handler processing (p. 350; Lec06). The signal currently being handled is also automatically blocked during handler execution (p. 350).
- `int sa_flags`: Option bitmask flags, including `SA_RESTART` (automatically restarts interrupted slow system calls) and `SA_SIGINFO` (passes extended signal information via `sa_sigaction`) (p. 350–351; Lec06).
- `void (*sa_sigaction)(int, siginfo_t *, void *)`: Alternate extended signal handler function pointer used when `SA_SIGINFO` is set in `sa_flags` (p. 350). _Reconstructed Slide Example 1 (Ignoring SIGINT):_

```
struct sigaction sact;
sact.sa_handler = SIG_IGN;
if (sigfillset(&sact.sa_mask) == -1) {
    perror("sigfillset");
    return 1;
}
sact.sa_flags = SA_RESTART;
if (sigaction(SIGINT, &sact, NULL) == -1) {
    perror("sigaction");
    return 1;
}
```

_Reconstructed Slide Example 2 (Running our Own Function):_

```
void my_handler(int signum) {
    /* ... */
}

struct sigaction sact;
sact.sa_handler = my_handler;
sact.sa_flags = SA_RESTART;
sigaction(SIGINT, &sact, NULL);
```

### 10.10 alarm and pause Functions
*pause Function Prototype (`<unistd.h>`):*
```c
int pause(void);
````

Returns -1 with **errno** set to `EINTR` (p. 338). _Semantics:_ Suspends the calling process execution until a signal is delivered whose disposition is to execute a signal handler or terminate the process (p. 338; Lec06). `pause` returns only after a signal handler executes and returns to the caller (p. 339; Lec06). _Unblock-and-Pause Race Condition:_ A common programming flaw attempts to protect code by blocking a signal, executing work, and then unblocking the signal immediately before calling `pause` (p. 339, 359; Lec06):

```
sigset_t set;
sigemptyset(&set);
sigaddset(&set, SIGINT);
sigprocmask(SIG_BLOCK, &set, NULL);
/* critical work */
sigprocmask(SIG_UNBLOCK, &set, NULL);
pause();
```

If a signal arrives during the timing gap between `sigprocmask(SIG_UNBLOCK)` and `pause()`, the kernel delivers the signal immediately, executing the signal handler (p. 339, 359; Lec06). When `pause()` subsequently executes, the signal has already been processed; `pause()` blocks execution indefinitely, waiting for a signal that may never arrive (p. 339, 359; Lec06).

### 10.16 sigsuspend Function

_Function Prototype (`<signal.h>`):_

```
int sigsuspend(const sigset_t *sigmask);
```

Always returns -1 with `errno` set to `EINTR` (p. 359; Lec06). _Atomic Mask Swap and Pause:_ `sigsuspend` sets the process signal mask to `sigmask` AND suspends the process until a caught signal arrives in a single, indivisible atomic operation in kernel space (p. 359; Lec06). This atomic operation completely eliminates the timing gap race condition inherent in separate `sigprocmask` and `pause` calls (p. 359; Lec06). _Handler Execution & Mask Restoration:_ When a caught signal arrives, `sigsuspend` invokes the registered signal handler first; upon handler return, `sigsuspend` automatically restores the process signal mask to its original value prior to the `sigsuspend` call and returns -1 (p. 359; Lec06). _Global Flag Synchronization:_ `sigsuspend` allows processes to sleep safely while waiting for a signal handler to set a global flag variable (e.g., `volatile sig_atomic_t quitflag`) without risking lost signals (p. 361–362).

### 10.19 sleep, nanosleep, and clock_nanosleep Functions

_sleep Function Prototype (`<unistd.h>`):_

```
unsigned int sleep(unsigned int seconds);
```

Returns 0 if the requested time elapsed, or the unslept duration in seconds if interrupted by a caught signal (p. 373; Lec06). _Implementation:_ Suspends process execution for `seconds` or until a caught signal handler returns (p. 373). Modern POSIX systems implement `sleep` using `nanosleep` to avoid interaction with `alarm` timers or `SIGALRM` signals (p. 373–374). _nanosleep Function Prototype (`<time.h>`):_

```
int nanosleep(const struct timespec *reqtp, struct timespec *remtp);
```

Returns 0 on success, or -1 on error or signal interruption (p. 374; Lec06). Provides nanosecond-level sleep precision using `struct timespec` (`tv_sec`, `tv_nsec`) without generating signals or interfering with system interval timers; if interrupted by a signal, `remtp` (if non-null) receives the unslept remaining time (p. 374–375; Lec06). _clock_nanosleep Function Prototype (`<time.h>`):_

```
int clock_nanosleep(clockid_t clock_id, int flags, const struct timespec *reqtp, struct timespec *remtp);
```

Returns 0 on success, or an error number on failure (p. 375). Evaluates high-resolution sleep delays against a specified system clock (`clock_id`, such as `CLOCK_REALTIME` or `CLOCK_MONOTONIC`) (p. 375). Setting `flags = TIMER_ABSTIME` executes an absolute time sleep (sleeping until the clock reaches a specific target timestamp), which eliminates cumulative scheduling drift in periodic application loops (p. 375).

### Signals Across fork and exec

_fork Signal Inheritance:_ When a process calls `fork`, the child process inherits an exact copy of the parent's process signal mask, signal dispositions, and installed signal handler addresses (p. 233, 326; Lec05). Pending signals for the parent are not inherited by the child; the child's pending signal set is initialized to empty (p. 233). _Process Signal Independence:_ Following `fork`, signal generation and delivery for parent and child processes are completely independent; delivering a signal to the parent does not affect the child, and vice versa (p. 326; Lec05). _exec Signal Modifications:_ When a process invokes an `exec` function, the current process memory image is replaced with a new binary executable image (p. 249, 325; Lec05).

- Process Signal Mask: Preserved across `exec` (p. 252, 325; Lec05).
- Ignored Signals (`SIG_IGN`): Remain set to `SIG_IGN` across `exec` because ignoring a signal requires no code execution in the new image (p. 325; Lec05).
- Caught Signals (Custom Handlers): Reset to their default action (**SIG_DFL**) because custom signal handler function addresses in the old memory space no longer exist within the new binary address space (p. 325; Lec05).

## Chapter Summary

UNIX signals provide an asynchronous software interrupt mechanism allowing processes to react to hardware faults, environment state changes, and process control events. _Mechanism:_ ==When a signal is generated for a process, the kernel sets a bit in its pending signal set and delivers the signal upon scheduling, executing default actions, ignoring the signal, or transferring execution to a sigaction handler while automatically updating the signal mask.== System calls interrupted by caught signals can be automatically restarted using `SA_RESTART`, atomic `sigsuspend()` calls eliminate mask-unblocking race conditions, and signal handlers must save/restore `errno` and restrict calls to async-signal safe functions to prevent memory corruption.

## Key Concepts

- **signal**: Asynchronous software interrupt delivered by the OS to notify a process of an event (p. 313; Lec05).
- **interrupt**: Hardware-generated CPU notification distinguished from software signals (Lec05).
- **null signal**: Signal number 0 used by `kill` for process existence and permission validation (p. 314).
- **disposition**: Action associated with a signal: default action, ignore, or catch (p. 315).
- **signal handler**: Custom user function registered to handle a caught signal (p. 315; Lec05).
- **core file**: Memory image file written to disk upon abnormal termination for debugging (p. 315).
- **SIGINT**: Signal 2 generated by Ctrl-C; default action is process termination (p. 316, 319; Lec05).
- **SIGFPE**: Signal 8 generated by arithmetic exceptions like divide-by-zero (p. 316, 318; Lec05).
- **SIGKILL**: Uncatchable, unblockable Signal 9 causing immediate process termination (p. 316, 319; Lec05).
- **SIGTERM**: Signal 15 requesting software termination; default `kill` command signal (p. 316, 321; Lec05).
- **SIGCHLD**: Signal 17 sent to parent when a child terminates or stops; ignored by default (p. 316, 317; Lec05).
- **SIGCONT**: Signal 18 resuming execution of a stopped process (p. 316, 317; Lec05).
- **SIGSTOP**: Uncatchable, unblockable Signal 19 pausing process execution (p. 316, 320; Lec05).
- **SIGUSR1** / **SIGUSR2**: User-defined signals reserved for application-specific logic (p. 322; Lec05).
- **SIGABRT**: Signal generated by `abort()` causing abnormal termination with core dump (p. 316, 317).
- **SIGALRM**: Signal generated when `alarm()` or `setitimer()` timer expires (p. 316, 317).
- **SIGBUS**: Signal generated by hardware or memory alignment faults (p. 316, 317).
- **SIGHUP**: Signal sent when controlling terminal disconnects; used by daemons to reload configs (p. 316, 318).
- **SIGILL**: Signal generated when executing an illegal CPU instruction (p. 316, 318).
- **SIGINFO**: BSD keyboard status request signal (Ctrl-T) (p. 316, 318).
- **SIGIOT**: Hardware fault signal generated by PDP-11 emulator trap or abort (p. 316, 318).
- **SIGPIPE**: Signal generated when writing to a pipe or socket with no active readers (p. 316, 319).
- **SIGQUIT**: Signal generated by terminal quit key Ctrl-\ generating a core dump (p. 316, 320).
- **SIGSEGV**: Signal generated by invalid memory references or segmentation violations (p. 316, 320).
- **SIGSYS**: Signal generated when making an invalid system call (p. 316, 320).
- **SIGTSTP**: Interactive terminal stop signal generated by Ctrl-Z (p. 316, 320; Lab 02).
- **SIGTTIN**: Signal generated when a background process attempts to read from controlling terminal (p. 316, 321).
- **SIGTTOU**: Signal generated when a background process attempts to write to controlling terminal (p. 316, 321).
- **SIGURG**: Signal generated when urgent out-of-band data arrives on a socket (p. 316, 322).
- **SIGWINCH**: Signal generated when the terminal window size changes (p. 316, 322).
- **pending**: Lifecycle state where a generated signal awaits delivery to the process (p. 335; Lec05).
- **delivered**: Lifecycle state where the kernel executes the signal disposition (p. 335; Lec05).
- **pending-signal coalescing**: Behavior where duplicate pending signals of the same type are dropped (p. 336; Lec05).
- **jobs** / **fg** / **bg** / **kill**: Shell job control commands managing background and stopped processes (Lab 02).
- **signal()**: Deprecated, non-portable C library interface for signal disposition setup (p. 323; Lec05).
- **SIG_ERR**: Error return constant `(void (*)())-1` from signal configuration calls (p. 325).
- **SIG_DFL**: Constant resetting signal disposition to its default system action (p. 323, 325).
- **SIG_IGN**: Constant setting signal disposition to ignore the signal (p. 323, 325).
- **raise**: Function allowing a process to send a signal to itself (p. 337).
- **slow system call**: System calls that can block indefinitely (e.g., terminal `read`, `pause`, `wait`) (p. 328; Lec06).
- **fast system call**: System calls that operate on disk I/O or return rapidly without blocking forever (p. 328).
- **EINTR**: Error code set when a slow system call is interrupted by a caught signal (p. 327; Lec06).
- **SA_RESTART**: `sigaction` flag automatically restarting system calls interrupted by signals (p. 329, 351; Lec06).
- ==**reentrant** / **async-signal safe**: Function property guaranteeing safe execution inside signal handlers without corrupting static data structures or heap memory (p. 330; Lec06).==
- **printf** / **malloc** / **free** / **strtok** / **getpwnam**: Standard non-reentrant functions unsafe inside handlers (p. 330–331; Lec06).
- **errno**: Global/thread-local error variable that must be saved and restored within handlers (p. 331; Lec06).
- **stat**: System call modifying `errno`, requiring `errno` preservation when called in handlers (p. 331; Lec06).
- **perror**: Error printing utility that can be corrupted if a handler overwrites `errno` (p. 331; Lec06).
- **sigset_t**: Primitive data type representing a bitmask collection of signals (p. 344; Lec05).
- **sigemptyset** / **sigfillset**: Functions initializing signal sets to empty or full (p. 344; Lec05).

## Worked Example

A robust `SIGCHLD` handler reaps all terminated child processes without creating zombies or blocking the main process:

```
#include "apue.h"
#include <sys/wait.h>
#include <errno.h>

void sigchld_handler(int signo) {
    int errno_save = errno;
    pid_t pid;
    int status;
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        /* child pid reaped successfully; process status if needed */
    }
    errno = errno_save;
}

int main(void) {
    struct sigaction sa;
    sa.sa_handler = sigchld_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    if (sigaction(SIGCHLD, &sa, NULL) < 0)
        err_sys("sigaction error");
    /* main program loop */
    for (;;)
        pause();
}
```

_Mechanism Explanation:_

1. _Non-blocking Loop (`WNOHANG`):_ Standard UNIX signals do not queue; if multiple child processes terminate simultaneously while `SIGCHLD` is blocked during handler execution, pending-signal coalescing drops extra `SIGCHLD` instances. ==Executing `while ((pid = waitpid(-1, &status, WNOHANG)) > 0)` inside the handler repeatedly reaps every available terminated child until waitpid returns 0, ensuring no zombie processes are left unreaped.==
2. _SA_RESTART:_ Setting `SA_RESTART` in `sa_flags` ensures that slow system calls interrupted in `main` by `SIGCHLD` delivery automatically resume rather than failing with `EINTR`.
3. _Preserving errno:_ When all dead children are reaped, `waitpid(-1, ...)` returns -1 and sets `errno` to `ECHILD`. Saving `errno` into `errno_save` at handler entry and restoring it before exit prevents `waitpid`'s `ECHILD` error from overwriting the `errno` state of interrupted main-line code.
