- Explain the three jobs any file system must implement on top of a raw block array: tracking which blocks belong to which file, tracking which blocks are free, and mapping names to metadata.
- Read and write a directory with `opendir`/`readdir`/`closedir`, and explain why there is no `writedir()`.
- Explain what actually changes on disk for each file operation (create, modify, rename, move) - which ones touch an i-node, which touch only a directory entry.
- Distinguish a hard link from a symbolic link by mechanism, not just behavior: what each one actually points at, and why only a symbolic link can cross file systems or dangle.
- Using [[20_Progress/Degree/CSCI 4061/Textbook/Chapter - 15|Chapter - 15]] and Lec08, write the `pipe()` + `fork()` + close-the-unused-end pattern from memory, and explain why each `close()` call is a message to the kernel, not just cleanup.
- State all six outcomes of the pipe read/write behavior table (open/closed on each end, data/space available or not) and explain the mechanism behind each.
- Explain `PIPE_BUF` and why writing more than it from multiple processes risks interleaved bytes.
## Key ideas (short)
- A file system's whole job is turning **one flat array of disk blocks** into a hierarchy, using **i-nodes** to store metadata separately from names and **directories** to supply the names.
- **Directories are files** - plain-looking (name, i-node number) pairs - so they get a dedicated read-only API (`opendir`/`readdir`) specifically so no program has to understand their internal layout to use them safely.
- A **hard link** is a second directory entry pointing at the same i-node; a **symbolic link** is an independent file holding a path string - only the second can dangle, point across file systems, or target something that doesn't exist yet.
- A **pipe** is two file descriptors sharing one kernel buffer - `close()` on either end isn't just resource cleanup, it's how a process tells the kernel (and therefore every other process sharing the pipe) "I will never read/write here again."
- **`PIPE_BUF`** is the write size under which the kernel guarantees no interleaving between concurrent writers - exceed it and bytes from different processes can genuinely interleave.

- **`total_dir_size()`** (Lec07 exercise, solved live in `lecture07-code/dir_size.c`): `opendir(".")`, loop `readdir()` until `NULL`, skip anything that isn't `DT_REG`, `stat()` each regular file and sum `st_size` - the canonical shape for "do something to every file in a directory" that `openat()`/`nftw()` later generalize to arbitrary paths and recursive subdirectories.
- **The pager-via-pipe program** (Chapter 15, Fig. 15.6): streams a file into `$PAGER` through a pipe instead of a temp file - the parent's final `close(fd[1])` after the last `write()` is simultaneously cleanup *and* the EOF signal the child's pipe-read is waiting for.
- **`process_files()` with a single shared pipe** (Lec08 exercise, solved live in `lecture08-code/single_pipe.c`): `n` children each `fork()`ed off a *single* pipe, each writing one `int` result to the shared write end before exiting; the parent closes its own write end, then `read()`s in a loop until it returns 0, relying on `PIPE_BUF` atomicity (`sizeof(int)` is nowhere near 512 bytes) to guarantee no child's 4-byte write ever interleaves with another's.
- **The word-frequency pipeline** (Lec08, recapping Lec04): `tr -cs A-Za-z '\n' | tr A-Z a-z | sort | uniq -c | sort -rn | head -n 10` - six small, sharply focused tools chained through five pipes, the lecture's running example for "the Unix philosophy."
## Lecture
### 1. Building a File System on Raw Blocks (Lec07, 9/29)
A file system has exactly three jobs on top of "an array of data blocks": track which (possibly scattered) blocks belong to each file, track which blocks are free (one bit per block - a free map), and build the directory hierarchy that maps human-readable names to that bookkeeping information. **I-nodes** solve the first and third problems together: a fixed-length record per file storing size, permissions, owner/group, and - organized as a tree of direct pointers, then single/double/triple indirect pointers as a file grows - the actual disk-block indexes holding its contents. An i-node conspicuously does **not** store the file's name; `stat()`/`fstat()` (`int stat(char *path, struct stat *statbuf); int fstat(int fd, struct stat *statbuf);`, 0 on success, -1 with `errno` set) are how a program actually reads that metadata into a `struct stat` it provides.
### 2. Why Fixed-Size Blocks, I-node Numbers, and the `ls -li` Picture (Lec07, 9/29)
Fixed-size-block allocation means growing or shrinking a file is just allocating or freeing blocks - no need to find one contiguous region of exactly the right size - at the cost of more bookkeeping to track which scattered blocks belong to which file. Every i-node gets a number giving its position in the i-node array; that number *is* effectively the disk block number for its metadata, visible directly via `ls -li` (the lecture's own real example: `25153730 -rw------- 1 jhkolb … file_list.c`, matching the same file permissions Week 2 already examined from a different angle). The number of bits used for i-node numbers caps the maximum number of files a file system can ever hold.
### 3. Directories and Path Resolution, Recap and Confirmation (Lec07, 9/29)
A directory is nothing more than a special kind of file whose contents are a list of (name, i-node number) entries - confirming exactly the picture [[20_Progress/Degree/CSCI 4061/Weekly/Week - 3|Week 3]] already built from Lec06's early preview. Lec07 re-walks `open("/home/sun/hello.txt")` i-node lookup by i-node lookup (root's known i-node → find `home`'s entry → find `sun`'s entry → find `hello.txt`'s entry) as direct confirmation, not new material - see Week 3's own Worked Example for the full step-by-step. **Directory permissions** get their own precise reading here: read lets you list entries, write lets you add/remove entries, execute lets you traverse through the directory as a path component - `x` alone means you can open a file inside it *if you already know the name*, but can't `ls` it.
### 4. The Buffer Cache, Confirmed from the OS Side (Lec07, 9/29)
A four-stage picture of what `read()`/`write()` actually touch: (1) a file is opened, its i-node copied into an i-node table entry; (2) `read()` completes by pulling from the **buffer cache** - a chunk of kernel-controlled main memory holding recently read/written blocks, not the disk directly; (3) `write()` completes by updating the buffer cache, not disk; (4) the OS eventually flushes dirty buffers to disk, either via an explicit `fsync()` call or automatically roughly every 15 seconds. This is the same buffering idea Week 2 covered from the stdio/kernel-write split; here it's one layer lower, inside the kernel's own disk-block caching.
### 5. The Directory API and the `total_dir_size()` Exercise (Lec07, 9/29)
Directories could technically be edited with plain `open`/`read`/`write`/`close`, but a dedicated API exists specifically so a systems programmer never has to understand a directory's actual on-disk layout to use one safely: `DIR *opendir(char *dirname);`, `struct dirent *readdir(DIR *dirp);` (repeat calls, `NULL` on end-of-directory or error, much like `strtok()`), `int closedir(DIR *dirp);`, `void rewinddir(DIR *dirp);`. There is deliberately no `writedir()` - directories are modified by adding or removing actual files, never by writing directory-entry bytes directly. The live exercise - compute the total byte size of every regular file in the current directory - is solved in full in `lecture07-code/dir_size.c`: `opendir(".")`, loop `readdir()` until `NULL`, check `d_type == DT_REG` to skip subdirectories and symlinks, `stat()` each matching entry and sum `st_size`. Generalizing to an arbitrary path needs `strcat`/`openat()` to build each file's full path (trivial in Python/Java, genuinely more work in C); generalizing to recurse into subdirectories has a ready-made library answer, `nftw()` ("file tree walk"), rather than hand-rolled recursion.
### 6. What Actually Happens on a File Operation (Lec07, 9/29)
A table worth memorizing directly: **creating** a file allocates a new i-node and adds a directory entry. **Modifying** a file allocates/frees data blocks to match its new size and changes the relevant block contents - the i-node's size field updates, but the i-node itself isn't replaced. **Renaming** a file only touches its directory entry; the i-node and data blocks never move. **Moving** a file to a different directory removes its entry from the source directory and adds an equivalent entry (same i-node number) to the destination - again, no change to the i-node or data blocks at all.
### 7. Hard Links and Symbolic Links (Lec07, 9/29)
Because a file's metadata/contents (i-node + data blocks) are stored separately from its name/location (a directory entry), the file-system "tree" can actually have multiple edges pointing at the same node - turning it into a DAG. A **hard link** is literally a second directory entry pointing at an existing i-node - every file already has at least one hard link, which is why an i-node keeps a reference count and only frees its storage once that count reaches 0. A **symbolic link** is a completely different file whose only content is a path string to another file, identified *by name*, not by i-node number - the i-node being pointed at has no idea any symlink points to it, which is exactly why deleting the target leaves a dangling symlink behind, something a hard link can never do. Terminal commands: `ln target new_name` (hard link), `ln -s target new_name` (symbolic link) - default to a symlink unless there's a specific reason not to. Matching system calls: `link()`, `symlink()`, `unlink()` (the name only really makes sense once you know it removes a directory entry, not necessarily the file itself), and `rename()`, guaranteed **atomic**.
### 8. Motivating Pipes (Lec08, 10/1)
Framed as a concrete problem first: a parent `fork()`s `n` children to process `n` files, and each child needs to report its result back to the parent - a bool, a single number, or a group of numbers, escalating in difficulty with plain exit-status-only tools. What's actually wanted: send arbitrary bytes (not just one numeric value), as many as needed, with no disk I/O, where the reader can tell when new data is actually available and the writer can tell if no one will ever read it - all through the familiar read/write interface. UNIX's answer: **pipes**.
### 9. `pipe()`, Pipe Internals, and Why Pipes Are Family-Only (Lec08, 10/1)
`int pipe(int filedes[2])` (-1 on error) hands back two descriptors sharing one kernel-managed memory buffer - `filedes[0]` read-only, `filedes[1]` write-only. Data written but not yet read sits in that buffer, capped at 16 pages on Linux (16 × 4096 = 65,536 bytes) - the lecture's explicit advice is to never rely on a specific capacity number and instead write programs that drain a pipe as soon as data is available. Pipes are **anonymous**: unlike a file, there's no path to `open()` them by - the only way to access one is to have created it or inherited its descriptors from an ancestor that did, which is exactly why `pipe()` then `fork()` is the standard pattern, and why this isn't a real limitation in practice (cooperating processes are almost always in the same family tree already).
### 10. Managing Pipe Descriptors as Communication, Not Just Cleanup (Lec08, 10/1)
The kernel tracks, in the global file table, how many processes still hold each end of a pipe open - which is exactly why `close()` on a pipe descriptor means more than freeing a resource. `close(pipe_fd[0])` tells every other holder of this pipe "I will never read here again"; `close(pipe_fd[1])` says the same for writing. That lets the kernel make real decisions: it makes no sense to keep letting someone read from a pipe with zero active writers, or write to one with zero active readers - both cases get special-cased behavior rather than hanging forever. The full behavior table: `read()` with data available returns the byte count regardless of write-end state; `read()` with no data and the write end still open **blocks**; `read()` with no data and the write end closed returns 0 (EOF); `write()` with buffer space available (read end open) returns the byte count written; `write()` with no buffer space (both ends open) **blocks**; `write()` with the read end closed raises `SIGPIPE` regardless of buffer space. The standard code shape: `pipe()`, `fork()`, child closes the end it won't use and does its work on the other, parent does the mirror image, both eventually close their remaining end.
### 11. Shell Pipelines, Revisited with Real Mechanism (Lec08, 10/1)
`ls -l | sort` is the shell forking a child for each command and wiring `ls -l`'s stdout to `sort`'s stdin with exactly `dup2(pipe_fds[1], STDOUT_FILENO)` / `dup2(pipe_fds[0], STDIN_FILENO)` - the same `dup2` mechanism Week 2 already covered for file redirection, just pointed at a pipe instead of a file. The six-stage word-frequency pipeline (`tr -cs A-Za-z '\n' | tr A-Z a-z | sort | uniq -c | sort -rn | head -n 10`) is the lecture's running example for composing small, sharply focused tools - five pipes chaining six programs, none of which was written with the others in mind.
### 12. FIFOs, Previewed Ahead of Their Assigned Week (Lec08, 10/1)
A **FIFO** is a pipe given a real name and a spot in the file-system tree, specifically to remove an ordinary pipe's biggest limitation - visibility only to the creator and its descendants, and disappearing the moment every holder closes it. Created with the shell's `mkfifo name` or the syscall `int mkfifo(const char *path, mode_t mode)`; processes `open()` it like a file, then `read()`/`write()` normally. Internally it's still memory-backed (an i-node exists, but no data blocks) - a special i-node field marks it as a named pipe for the kernel's own special handling, the same trick that marks a symbolic link. Two real oddities: opening with `O_RDONLY` blocks until *some* other process opens it for writing, and vice versa, so a careless FIFO program can hang forever waiting for a partner that never shows up. **This is book §15.5, not assigned reading this week** - see [[20_Progress/Degree/CSCI 4061/Textbook/Chapter - 15|Chapter - 15]]'s Connections section for why it's flagged rather than folded into the chapter note.
### 13. Solving the Exercise: One Pipe, Then an Array of Pipes (Lec08, 10/1)
`int process_files(char *file_names[], int n)` - solved first with a **single shared pipe**: every one of `n` forked children writes its one `int` result to the same write end before exiting, and the parent, after closing its own copy of the write end, loops `read()` until it returns 0, collecting every child's result in whatever order they happen to finish. This works safely only because each write (`sizeof(int)` = 4 bytes) is nowhere near `PIPE_BUF` - any POSIX system guarantees atomicity up to 512 bytes, Linux specifically guarantees it up to 4096, so none of the `n` children's writes can ever interleave with another's. `lecture08-code/single_pipe.c` is this exact solution, including the full error-path cleanup (closing both descriptors and reaping already-forked children before returning -1 on a `fork()` failure partway through the loop). A second version solves the same problem with an **array of pipes**, one dedicated pipe per child: `int *pipe_fds = malloc(2*n * sizeof(int));`, then `pipe(pipe_fds + 2*i)` initializes pipe `i`, after which `pipe_fds[2*i]`/`pipe_fds[2*i + 1]` are that pipe's read/write ends. The lecture's own verdict: a single shared pipe is simpler and sufficient whenever atomicity holds (attach the child's PID to each message if you need to know who sent what) - reach for an array of pipes mainly when a single write could exceed the atomicity threshold. **Project 2 requires the array-of-pipes version.**

## Lecture-to-textbook synthesis
- ==Everything this week - i-nodes, directories, links, pipes - is the same idea applied at two different layers: separate a thing's *identity and content* (an i-node's metadata and blocks; a pipe's kernel buffer) from the *name or handle* used to reach it (a directory entry; a file descriptor), and nearly every mechanism this week exists to manage what happens when that separation gets exploited or broken.==
- *Mechanism:* A hard link exploits the i-node/name separation deliberately - two names, one identity, reference-counted so the content survives until the last name is gone. A dangling symlink is the same separation failing honestly - the name survives, the identity doesn't, and nothing detects that until something tries to resolve it. A pipe's `close()` calls manage an analogous separation on the IPC side: the kernel buffer (identity) keeps running until every descriptor (handle) pointing at either end is gone, and each `close()` is how a process declares it's permanently done with its handle.
- Lecture example/scenario: the `proj1-code`/`proj2-code` shared-inode picture makes the file-system version concrete (two names, `0x0004` and `0x0008`, one identity each); `single_pipe.c`'s parent-closes-write-end-then-reads-until-EOF loop makes the IPC version concrete - the parent's own close is what eventually turns an endless `read()` loop into one that terminates.
- Textbook connection: [[20_Progress/Degree/CSCI 4061/Textbook/Chapter - 4|Chapter - 4]] formalizes the i-node/directory-entry separation this week's lecture re-confirms in detail; [[20_Progress/Degree/CSCI 4061/Textbook/Chapter - 15|Chapter - 15]] formalizes the pipe-buffer/descriptor separation and its close-as-signal consequence, both now source-checked.
- Concept links: none yet - see Concepts created today above.
> [!WARNING]
> Assuming a symbolic link "is" the file it points to, the way a hard link effectively is, is the single most costly mix-up this week invites. Deleting a hard-linked file's original name leaves the content fully intact under its other name(s); deleting a symlink's *target* leaves the symlink itself sitting there, now pointing at nothing - `ls` will still show it, `cat` will fail with a "No such file or directory" that looks like the link itself is broken, when actually the link is working exactly as designed.
> [!SUMMARY]
> Week 4 is the week identity gets separated from name twice over - once for files (i-node vs. directory entry, the mechanism behind every link, rename, and move) and once for interprocess communication (a pipe's kernel buffer vs. the file descriptors referencing it, the mechanism behind every `close()` call actually mattering) - setting up the rest of the IPC unit (shared memory, then threads) as more of the same separation applied to raw memory instead of files.
## Flashcards
#cards/csci4061
Why does an i-node never store a file's own name?::Storing the name separately in a directory entry is what allows multiple directory entries (hard links), potentially in different directories, to point at the identical i-node without needing to duplicate or keep synchronized copies of the file's metadata.
Renaming a file with `rename()` versus moving it to a different directory - what do both operations leave completely untouched?::Both only modify directory entries (removing from one location and/or adding to another, same i-node number throughout) - neither the i-node nor the file's actual data blocks are read, written, or reallocated by either operation.
What does `close(pipe_fds[1])` actually communicate to the kernel, beyond freeing a file descriptor?::It declares that this process will never write to this pipe again. The kernel uses that declaration to decide what should happen to any reader still blocked on the other end - once every write-end holder has made this declaration, a blocked `read()` returns 0 instead of waiting forever.
A child writes a 4-byte `int` result to a shared pipe that two other sibling children are also writing to concurrently. Why is this guaranteed not to interleave with their writes?::4 bytes is far under `PIPE_BUF` (512 bytes guaranteed on any POSIX system, 4096 on Linux) - the kernel guarantees that any single write at or under that size completes as one atomic, uninterleaved operation, regardless of how many other processes are also writing to the same pipe.
Why does a FIFO opened with `O_RDONLY` block even though the file already exists on disk?::A FIFO's `open()` semantics are deliberately different from a regular file's: `O_RDONLY` blocks until some other process has opened the same FIFO for writing (and vice versa for `O_WRONLY`), since a FIFO with no writer on the other end has nothing meaningful to read yet.
What's the real difference between what a hard link and a symbolic link actually point at?::A hard link is a second directory entry pointing directly at the same i-node number as an existing file - no indirection, same file system required. A symbolic link is its own separate file whose contents are a path *string* naming another file by location, resolved through an extra lookup step, which is exactly what lets it dangle, cross file systems, or target a path that doesn't exist yet.
