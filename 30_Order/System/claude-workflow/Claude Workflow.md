# Claude Workflow
## Purpose
Local automation around Claude Code in the Jarvis vault: four hook scripts, the transcript exporter, and the scheduled jobs that commit the vault, back-fill missed sessions and run the weekly review. If it stops, sessions are not captured, writes are not guarded, PDFs can flood the context, and the git history and GitHub backup stop growing. The standing contract: Claude Code is the implementation surface, Claude Desktop is read-first planning, mobile is capture only, and MCP retrieves small context packs, not the whole vault.

## Inputs and Outputs
Reads hook JSON on stdin, Claude Code and Cowork transcripts, and the git repo. Writes exported sessions to `60_Claude/05_Clippings/AI Conversations/<Machine>/Windows/Claude/<project>/` (format in [[Conversations]]), where `<Machine>` comes from the host name inside `export-claude-session.ps1` (two names are mapped, and an unknown host writes nothing), a capture-health note `60_Claude/05_Clippings/AI Conversations/00 - Capture Health.md` after each backfill run, `logs/` in this folder, a machine-local hook activity log at `%USERPROFILE%\.claude\jarvis-session-activity.jsonl`, and git commits. The session log is not written here. No hook or script in this folder appends to `60_Claude/07_AI_Information/Session Logs/log.md`: the write guard only allows writes to it. `jarvis-session-activity.jsonl` is hook activity data (event, session id, export outcome), not the session log. The one writer of the session log is the agent or skill that ran the session, which appends one entry at its end (see [[Memory Management]]); the weekly review does so through its own Step 8 when the scheduled task runs it. The write guard denies new root files and writes into `50_Archive/`, `60_Claude/05_Clippings/`, `.obsidian/`, `.cursor/`, `.kiro/`, and `.git/`, with an allowlist for the daily-operations paths. The internship guard checks required frontmatter fields on internship notes and reports a gap as context; it never blocks. `claude_desktop_config.read-first.example.json` is a reference config for Claude Desktop, not a secret store. `.mcp.json` at the vault root (git-ignored) registers the `jarvis` server only: transport `http` to `127.0.0.1:27123` with an `Authorization` header. That port belongs to the Obsidian Local REST API plugin (`obsidian-local-rest-api`, enabled in this vault), so `jarvis` is up only while Obsidian runs with that plugin. On 2026-11-04 it failed to connect at session start with `ECONNREFUSED` because Obsidian had been restarted at about 00:52 and was not yet listening; by 02:15 the port answered 200. A request with the stored header then returned 401, so the stored credential is not accepted by the plugin now (I did not open or print it). Nothing in this folder can fix that: the key in the plugin's settings and the header in `.mcp.json` have to match, and the owner holds both.
Paths: the write guard, the internship guard, the continuity hook (the PDF guard instead finds `scripts\mineru-pdf.ps1` as a sibling folder), `git-auto-sync.ps1`, the two exporters, `update-capture-health.ps1` and `run-weekly-review.ps1` find the vault by going four folders up from themselves (`$PSScriptRoot\..\..\..\..`), so this folder must stay at `30_Order/System/claude-workflow/`. ## Failure Behavior
The write guard, the PDF guard and the continuity hook fail open: a parse problem exits 0, and an export error never blocks Claude Code from exiting. The internship guard reports a gap as context and never blocks. `git-auto-sync.ps1` exits 1 on a real problem (a pull-rebase conflict, a push that fails twice, a stale lock) and writes a final `=== git-auto-sync end (FAILED, ...) ===` line; it aborts a failed rebase instead of leaving the repo mid-rebase, and treats a lock older than 30 minutes as stale. The weekly review skips when its lock is under 120 minutes old. Each VBS launcher waits and returns the real exit code, so Task Scheduler's last result is honest. A failed sync is surfaced by the banner described in the sync-workflow record.
## Verify
```powershell
Get-ScheduledTask -TaskName Jarvis-GitAutoSync, Jarvis-WeeklyReview | Get-ScheduledTaskInfo
Get-Content 30_Order\System\claude-workflow\logs\git-auto-sync.log -Tail 5
```
The last result is 0 and the last line reads `=== git-auto-sync end (success) ===`, `(nothing to do)`, or `(deferred, ...)`; any `(FAILED, ...)` needs a human. On 2026-11-04 at 00:33 the last result was 1 and the log showed a commit followed by `=== git-auto-sync end (FAILED, local changes could not be committed) ===`, so the check at `git-auto-sync.ps1` line 399 to 405 found changes still unstaged or uncommitted after the commit. The log keeps no git error text for that branch, so I could not read the cause of the 2026-11-03 23:03, 23:33 and 2026-11-04 00:33 failures; each came straight after a successful commit, which fits a tracked file (a live session export) changing between `git add` and the check, but I did not prove that. One cause I did reproduce: at 02:38 on 2026-11-04 a stray file named `nul` (made by a shell command of mine redirecting to `/dev/null` from Git Bash into Node) sat in `30_Order/Templates`; `git add` printed `unable to index file '30_Order/Templates/nul'` and the script ended with the same `FAILED, local changes could not be committed` line. After I deleted that file the next run committed and pushed. Any untracked file with a Windows reserved name (`nul`, `con`, `aux`, `prn`, `com1`) does this, and the sync banner reports it. The sync-workflow banner reported the 00:33 failure. The later runs ended `nothing to do` (02:03 and 02:16) and `success` (a commit and a push at 02:29, `branch: master`, `Pushed cleanly to origin/master`). The test harness `scripts/run-all-tests.ps1` ran 18 of 18 passing (nine tests under `pwsh` and `powershell`) before and after the 2026-11-04 path edits. Compare the number of Claude Code sessions in `~/.claude/projects` with the notes in the Windows export folder. In a Claude Code session, `/hooks` should list the write guard, the internship guard, the PDF guard (three entries) and the continuity hook (SessionStart, Stop and SessionEnd). To test SessionStart by hand, pipe `{"hook_event_name":"SessionStart","cwd":"<vault path>"}` into the hook: it prints one JSON object inside the Jarvis folder and nothing elsewhere.
