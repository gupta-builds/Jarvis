# Sync Workflow
## Purpose
Answers one question every five minutes: is the vault folder really synced between the laptops right now, and is git still committing it? Syncthing keeps the working tree converged in real time and git-auto-sync records history, so a silent failure of either leaves the two laptops quietly different. A Task Scheduler exit code is not a warning if nothing shows it, so this check raises a banner and a toast.
## Trigger
`Jarvis-Syncthing-Health` repeats every 5 minutes (a 3650-day repetition from 2026-09-20) and runs `scripts/check-syncthing-status-silent.vbs`, which runs `scripts/check-syncthing-status.ps1` hidden, waits, and returns its real exit code. No registration script is kept in this repo; the task was created by hand, so recreate it from the values above on a new machine. `scripts/rotate-sync-logs.ps1` is run manually. The git half of sync runs on one branch: `git-auto-sync` commits and pushes `master` to `origin/master`, the only branch on GitHub (the old `infra/cross-laptop-sync` branch was deleted on 2026-11-05).
One script here has nothing to do with sync. `scripts/codex-daemon-guard.ps1`, launched by `scripts/codex-daemon-guard-silent.vbs`, keeps the Codex background server startable: if `codex app-server daemon version` fails, it deletes the stale pid files and sockets under `~/.codex` and starts the daemon again. Its task, `Jarvis-Codex-Daemon-Guard`, was created by hand (no registration script exists), runs at logon and every 15 minutes, and on 2026-11-04 was **Disabled**: last run 2026-10-26 18:57 with result 0, and 795 missed runs. It finds `codex.cmd` on PATH, then in `CODEX_CMD`, then in npm's global prefix (asked from `npm config get prefix`), then in `%APPDATA%\npm`; it used to fall back to one fixed folder on drive D (fixed 2026-11-04 and tested by calling the function, the task itself is still disabled). It is documented here only because its files live in this folder, and it does not feed the sync banner.
## Inputs and Outputs
Reads Syncthing's REST API (`http://127.0.0.1:8384`, folder id `jarvis`) with the API key from `%LOCALAPPDATA%\Syncthing\config.xml`, and the tail of `30_Order/System/claude-workflow/logs/git-auto-sync.log`. It reports a problem when Syncthing is not running (and tries to start it), the GUI listener on port 8384 is owned by something other than exactly one Syncthing process, the API is unreachable, the folder still needs files or bytes or has errors, live `*.sync-conflict-*` files or stuck `~syncthing~*.tmp` files exist (`.stversions` and `99_Archive` are excluded), a remote device cannot be reached, or git-auto-sync's latest run ended `FAILED`. On a problem it writes `Sync Alert Banner.md` in this folder and, once, a static embed line into `00_Dashboard.md` between `<!-- SYNC-ALERT:BEGIN -->` and `<!-- SYNC-ALERT:END -->`, so the changing text never edits the dashboard itself. It sends a Windows toast on first detection and then every 12th tick (hourly), and a recovery toast when it clears. Exit 0 means synced (or no remote device yet); exit 1 means a problem.
`rotate-sync-logs.ps1` trims the Unison `Sync-Log.md` files (`20_Progress/AI/Claude Code/*/Sync-Log.md` and `_All-Projects-Sync-Log.md` if it exists) to 7 days by default. It is a dry run unless `-Apply` is passed, and moves old lines into `Sync-Log-Archive-<date>.md` next to the source; nothing is deleted. Run `-Apply` only when no sync is writing the file.
## State
Ignored by git, each by a line in the root `.gitignore`: `Sync Alert Banner.md` (line 112; generated; its content changes per machine), `scripts/.sync-alert-state.json` (156; the consecutive-failure count that rate-limits toasts), and `scripts/.syncthing-exe-path.txt` (163; a cache used to restart Syncthing). The banner is exempt from Standards because a script rewrites it and it is empty when everything is healthy. The Codex guard writes `%LOCALAPPDATA%\codex-guard\guard.log` outside the vault, only when something was wrong, and trims it to 200 lines once it passes 300.
## Failure Behavior
It always reaches the alert step; it never exits early before the problem list is built. A failed toast never changes the exit code. If Syncthing's config or API key is missing it reports that as a problem and exits 1. The launcher returns the real exit code, so the task's last result is 1 while a problem stands. A problem it cannot fix itself needs a human: read each conflict file against its canonical copy before touching it, and never bulk-discard.
**Owner step, not run, before the Dell pulls or its git writer is re-enabled.** On 2026-11-05 the Acer untracked every AI conversation export (1,673 files under `60_Claude/05_Clippings/AI Conversations/`, commit `56d960d2`; the files stay on the Acer's disk and in history, and `.gitignore` now ignores that tree except its README). The Dell's index still tracks them, so a plain `git pull` there deletes the Dell's copies, and Syncthing, which still syncs that tree, could then carry those deletions to the Acer. In this order: (1) pause the `jarvis` folder in Syncthing on the Dell; (2) copy `60_Claude/05_Clippings/AI Conversations/` to a folder outside the vault; (3) keep `Jarvis-GitAutoSync` disabled and run `git pull --ff-only origin master` by hand; (4) restore the copied folder over the vault one; (5) check that `git status` lists nothing under that tree and that `git check-ignore -v` names the new `.gitignore` rule for one restored note; (6) resume the Syncthing folder and only then consider re-enabling the git writer. I did not run any of this and took no action on the Dell. Recommendation: do it on the Dell in one sitting, and add `(?d)60_Claude/05_Clippings/AI Conversations/**` to `.stignore` on both laptops afterwards if the notes should stay per machine (the Conversation Layer note lists that as still open).
## Verify
```powershell
Get-ScheduledTask -TaskName Jarvis-Syncthing-Health | Get-ScheduledTaskInfo
powershell -File 30_Order\System\sync-workflow\scripts\check-syncthing-status.ps1
```
A healthy run prints the folder state with `needFiles : 0` and exits 0, and the banner file is empty. Make one deliberate test change on the other laptop and confirm it arrives and the banner stays clear. On 2026-11-04 at 00:51 the last result was 1 and the banner listed two problems: Syncthing "was not running" and the latest `git-auto-sync` run ended `FAILED`. The second was real (the `00:33` log line in the claude-workflow record). The first was false: Syncthing had been running since 2026-11-03 11:36, with the folder idle, 0 files needed and the other laptop at 100%. The cause was the check, not Syncthing. On this machine the socket on `127.0.0.1:8384` flaps between `LISTENING`, `FIN_WAIT_1` and absent in `netstat` and `Get-NetTCPConnection` while the GUI and API answer normally (8 samples at 3-second spacing showed `LISTENING` once), and the script took "no `LISTENING` row" to mean "not running", exited 1 and started a redundant second `syncthing serve`. Fixed the same day: with no listener row, the script now accepts a running `syncthing` process plus an `OK` from the unauthenticated `/rest/noauth/health` endpoint, prints that it did so, and starts nothing. Five consecutive hand runs afterwards printed `IN SYNC`, exited 0 and left the banner empty, and the scheduled task's next run (2026-11-04 02:26) recorded result 0. The actual TCP flapping is a Windows or network-stack oddity outside this folder and is not explained.
