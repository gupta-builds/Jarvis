# Cross-Laptop Sync - Build 2 Findings
## One-Line Answer
==The conflict-copy safety net is real on a genuine two-device sync, but it only protects an edit Syncthing's own watcher has already noticed== — an edit made in the short window before that happens gets silently overwritten by an incoming remote change, with no `.sync-conflict-*` file and no `.stversions/` entry, exactly like Build 1's single-device test, just proven now on a real second device instead of assumed to generalize.
## Test Setup
Two independent Syncthing v2.1.5 processes on this Dell, each with its own `-home` (config, cert, key, device ID), so each is a genuinely separate device, not a second window on the same identity:
- Instance A: home `C:\SyncTest\config-A`, GUI `127.0.0.1:8385`, sync listener `tcp://127.0.0.1:22001`, device ID `H5OLYCE-...-ETHZQQD`.
- Instance B: home `C:\SyncTest\config-B`, GUI `127.0.0.1:8386`, sync listener `tcp://127.0.0.1:22002`, device ID `53XM3Y4-...-ETLZOAP`.
Both had `globalAnnounceEnabled`, `localAnnounceEnabled`, and `relaysEnabled` set to `false` in `config.xml`, and were paired only through a static `tcp://127.0.0.1:<port>` address on each device's own entry for the other — no internet discovery, no relay, confirmed connected (`rest/system/connections` showed `isLocal: true`, `type: tcp-server`/`tcp-client`) within seconds of both processes starting.
A single shared folder, id `synctest` (never the real `jarvis` folder ID), pointed at `C:\SyncTest\InstanceA` and `C:\SyncTest\InstanceB` — disposable directories outside the vault, holding a handful of small `.md` files, nothing sensitive. Staggered versioning was on with `maxAge: 0`, matching the real vault's config.
The real primary Syncthing instance (`%LOCALAPPDATA%\Syncthing`, GUI `127.0.0.1:8384`, folder `jarvis` at `D:\Users\_Anant\10_Areas\Documents\Jarvis`) ran the whole time, untouched, confirmed by its own REST API before and after: folder list still shows only `jarvis` at the same path, `errors: 0`, file/byte counts unchanged apart from the vault's own ordinary background growth during this session.
## What Actually Happened
**Finding 1 — the documented conflict-copy mechanism is real, not a Build 1 assumption.** With both folders paused, `note1.md` was edited independently on A and B to different content, then both folders unpaused at once so the changes met each other for the first time. Within seconds, both instances produced `note1.sync-conflict-20260919-002240-53XM3Y4.md`. `note1.md` itself ended up holding B's text; the conflict-copy file held A's — nothing was lost, exactly the behavior [Syncthing's versioning docs](https://docs.syncthing.net/users/versioning.html) describe, now confirmed against two real devices instead of one.
**Finding 2 — the exact race Build 1 flagged still loses silently, even cross-device.** To reproduce "an edit Syncthing hasn't noticed yet" deterministically (sub-second timing isn't reliable to script), Instance A's folder had `fsWatcherEnabled` set to `false` and `rescanIntervalS` set to `3600` before writing new content to `note2.md` on A — so A's own database never learned the file had changed. Immediately afterward, `note2.md` was edited on B and pushed to A. A's copy was silently replaced with B's content. No `.sync-conflict-*` file appeared, and no `.stversions/` folder was created at all. **A's edit was gone, with the exact same silence Build 1 found on a single machine** — a genuine remote-driven replace did not save it.
**Finding 3 — Staggered Versioning itself works; it's gated on Syncthing's own database, not on "was this remote-driven."** As a control, `note3.md` was allowed to sync normally and sit idle (A's watcher back on, both sides confirmed in sync) before B edited it again. This time `.stversions/note3~20260919-002634.md` appeared on A holding the pre-replace content. The difference between Finding 2 and Finding 3 is not "remote vs local" — both were genuine remote-driven replaces — it's whether A's database already had the current file scanned and recorded before the incoming change arrived. If it had, the puller versions the old copy before overwriting. If it hadn't — because the local edit was still sitting in the fsWatcher's detection delay, or the watcher was off — the puller overwrites without versioning anything, because as far as Syncthing's own bookkeeping is concerned nothing local had changed.
**Finding 4 — pairing two instances over pure localhost TCP needs no discovery or relay infrastructure**, confirmed live: with `globalAnnounceEnabled`, `localAnnounceEnabled`, and `relaysEnabled` all `false`, both instances still found and connected to each other purely through the static `tcp://127.0.0.1:<port>` address in each device's config, matching the forum guidance found ([Syncthing forum — multiple instances](https://forum.syncthing.net/t/how-do-i-run-multiple-syncthing-processes-on-the-same-machine/19574), [Syncthing forum — pairing without discovery](https://forum.syncthing.net/t/two-syncthing-instances-in-one-machine/16162)) that each instance just needs its own `-home`, its own ports, and a static address for the other side.
**Finding 5 — teardown left no trace.** Both test processes were stopped by PID (confirmed by command line via `Get-CimInstance Win32_Process`, not by name alone, so the real primary instance's PIDs were never touched), then `C:\SyncTest` was removed entirely. The primary instance's folder list, file count, and error count were checked before the test started and again after teardown — folder list still shows only `jarvis`, `errors: 0`, no `synctest` folder ever appeared on the primary.
**Finding 6 — Syncthing now has a Scheduled Task and starts at logon**, using the official steps ([Syncthing autostart docs](https://docs.syncthing.net/users/autostart.html)): trigger "At log on" for this Windows user, action `syncthing.exe serve --no-console --no-browser`, execution time limit disabled (the default 3-day auto-kill would otherwise stop a long-running daemon), logon type "Interactive only" so no stored credential is needed. Triggering the task manually while the primary instance already held its ports produced `Last Result: 1` — confirmed via `schtasks /query /v` to be the expected port-bind conflict with the already-running primary, not a task misconfiguration, since the action's command line matched exactly what was registered. **What this finding cannot confirm:** an actual cold-boot or log-off/log-on cycle was not run, and a live test that stopped the primary process to free its ports for a clean run was blocked by this session's own safety classifier ("Interfere With Workloads") — correctly, since that would have briefly touched the real running sync process. The task is registered and its action is verified correct; a true reboot test is still open.
## What Build 3 Must Still Weigh
Build 1 already found Obsidian flushes typed edits to disk within seconds, not on an explicit save — so the dangerous window this build identifies (between a local edit landing on disk and Syncthing's watcher noticing it, governed by `fsWatcherDelayS`) is short, but Finding 2 shows it is not zero, and nothing inside Syncthing closes it. The practical mitigation is procedural, not technical: avoid having both laptops edit the same note within roughly the same few seconds, and treat `.stversions/` as reliable only for changes that had already synced and settled before the next edit arrived — not as a guarantee against a genuinely fresh, still-unscanned edit losing a race.
