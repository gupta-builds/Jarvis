  ## Specific confusion points / traps for flashcard material
  
  1. **The `f(x,y)` reentrancy trace resolves to 19, 19 — not 7, 19** in the specific interleaving where the signal arrives mid-execution of the *first* call to `f`. Students who assume "the interrupted call finishes with its own original values" will get this wrong; the actual mechanism is that the global `z` gets overwritten by the *second* (handler's) call before the *first* call's `return z` statement ever executes, so the first call also returns the handler's value.
  2. **`SA_RESTART` does not protect against reentrancy** — it only resumes an interrupted *system call*, unrelated to a handler calling a non-reentrant *function* concurrently with main-line code. Direct instructor quote: "it doesn't address this kind of issue."
  3. **Signals cannot be counted** — `SIGUSR1` sent twice while already pending delivers as one invocation; this specifically breaks any scheme that tries to use raw signal delivery as a counting mechanism (explicitly surfaced in the Lec08 "how would children report results" discussion as the reason signals lose to pipes for this use case).
  4. **readdir() NULL is ambiguous** between end-of-stream and a real error unless you zero `errno` before the call and check it after — genuinely not covered in the slides, sourced live from the man page in front of the class.
  5. **Partial pipe writes near the capacity boundary** are not crisply specified even by the instructor himself ("my guess would be...") — a question like "what does `write()` return if you ask for 16 bytes but only 12 bytes of buffer space remain" has no confidently-stated single correct numeric answer from this course's own material, making it a good discussion/essay-style question but a risky multiple-choice one.
  6. **`unlink()`'s name only makes sense once you know what it does** — it removes a *hard link* (a directory entry), not necessarily the underlying data; data is only freed once `st_nlink` reaches 0 AND no process has the file open.
  7. **`~` works in the shell, never in C** — `open("~/foo.txt", ...)` fails because `~`-expansion is a shell-only convenience; C code must use `getenv("HOME")`.
  8. **`exit()` not `return`/`break` inside a forked child's work function** — returning normally from a helper function called by all `n` forked children would let every child fall through and execute the parent's post-fork code too, producing duplicate output/behavior.
  9. **Lab 3's own quiz answer confirms:** the correct way for a handler to signal `main()` is "change the value of a global variable" (ideally `volatile sig_atomic_t`) — not printf, not recursion, not a second signal.

  ## Specific Confusion Points / Exam-Depth Traps
  
  - Two unrelated processes opening the same path do **not** share an offset; only a `fork()` relationship shares the system-file-table entry.
