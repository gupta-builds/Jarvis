### Question 1(a) — Process tree for `./par ls date who`

**Exam-style answer**
```
        bash
          |
         par
        / | \
      ls date who
```
`bash` is the shell that launches `par` via `fork()`+`exec()`. `par` itself then `fork()`s three children (one per command-line argument), each of which `exec()`s a different program (`ls`, `date`, `who`) without spawning further children.

**Why this is correct**
`fork()` creates a new process; `exec()` replaces that process's program image while keeping its PID. Each node in the tree is a process; the label is whatever program it is currently executing. Since `par` forks once per command and each child execs immediately, the three leaves are siblings under `par`, which is itself a child of `bash`.

### Question 1(b) — `par`'s `main()`

**Exam-style answer**
```c
int main(int argc, char *argv[]) {
    int out_fd = open("out.txt", O_CREAT|O_TRUNC|O_WRONLY, S_IRUSR|S_IWUSR);
    for (int i = 1; i < argc; i++) {
        pid_t child_pid = fork();
        if (child_pid == 0) {
            dup2(out_fd, STDOUT_FILENO);
            execlp(argv[i], argv[i], NULL);
        }
    }
    close(out_fd);
    for (int i = 1; i < argc; i++) {
        wait(NULL);
    }
    printf("Commands Complete\n");
    return 0;
}
```

**Why this is correct**
Open `out.txt` once in the parent (so every child redirects to the *same* underlying file via a shared fd, matching "overwritten if it already exists" via `O_TRUNC`). Fork once per argument; each child redirects its stdout to that fd with `dup2()` before `exec()`ing the named program (found via `PATH` since `execlp` searches it). The parent closes its own copy of `out_fd` once all children are forked (it doesn't need it), then `wait()`s once per child before printing the completion message — guaranteeing all commands finished before "Commands Complete" prints.

### Question 1(c) — Daemon / Orphan / Zombie

**Exam-style answer**

| Sub-question | Answer |
|---|---|
| (i) the `par` process itself | **Zombie** only |
| (ii) `ls`/`date`/`who` (with `par` waiting, as specified) | **Zombie** only |
| (iii) `ls`/`date`/`who`, if `par` is changed to *not* wait | **Daemon**, **Orphan**, and **Zombie** (all three) |

**Why this is correct**
`bash` runs `par` in the foreground and (as an interactive shell) waits for it — so after `par` finishes and `exit()`s, it sits as a zombie until `bash` calls `wait()` on it; it can never become an orphan (bash outlives it in normal use) or a daemon (it's a one-shot foreground command, not a never-waited background service). The same reasoning applies to `ls`/`date`/`who` under `par`'s original (waiting) design.

If `par` stops waiting for its children: once `par` exits and its children are still running or about to exit, they become **orphans** (adopted by `init`/`systemd`); after they exit, they briefly become **zombies** until `init` reaps them; and because `par`'s parent (`par` itself, while alive) never calls `wait()` on them at all, they also satisfy the course's own literal definition of a **daemon** ("a process whose parent forks it and never waits for it at all"), even though they are not long-running services in the traditional sense.

### Question 2(a) — `fork()` then unconditional `write(message1)`

**Exam-style answer**
Contents: **`Hello 4061Hello 4061`** (20 bytes, unique — `N/A` for "different contents possible").

**Why this is correct**
`fork()` happens *before* the `write()` call, so both parent and child execute the identical `write(fd, message1, …)` line — there's no branch distinguishing them. Both write "Hello 4061" into the *same* file, through file descriptors that (because the fd was opened before the fork) share the **same system-file-table entry and the same file offset**. ### Question 3 — File Systems (`cp`/`mv`/`ln`/`ln -s`/`rm` sequence)

|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|

| (g) `rm minitar_code.c` | | ✓ | | | | | | ✓ |
| (h) `rm minitar_new.c` | | ✓ | | ✓ | | ✓ | | |

**Why this is correct**

Tracking the hard-link chain: after (c), `minitar_new.c` and `minitar_code.c` share one inode at ref-count 2; (g) drops it to 1 (not yet freed); (h) removes the last reference, freeing it.

### Question 4(a) — Two problems with the `SIGINT` handler calling `stat()`/`printf()`

**Exam-style answer**
1. **`errno` clobbering.** If `getcwd()` in `main()` fails and sets `errno`, and then `SIGINT` arrives before `main()` checks `errno` (e.g., before `perror("getcwd")` runs), the handler's own `stat()` call can fail and overwrite `errno` — so `main()`'s subsequent `perror()` reports the *wrong* error.
2. **Non-reentrant `printf()`.** Both `main()` (via `printf("Current directory is: …")`) and the handler (via `printf("test.txt size: …")`) call `printf()`, which is not reentrant. If `SIGINT` interrupts `main()`'s `printf()` call mid-execution, the handler's own nested `printf()` call can corrupt stdio's internal buffering state, producing garbled output or, in the worst case, a crash.

**Why this is correct**
Both hazards follow directly from the same root cause: a signal handler genuinely interrupts whatever code was running, mid-instruction, so any shared, non-reentrant state it touches (a global `errno`, stdio's internal buffers) can be corrupted by the handler running "inside" an in-progress call to the same function or facility.

**Local source evidence**
- `20_Progress/Degree/CSCI 4061/Weekly/Week - 3.md`
  - §7 "Tricky Item 2: `errno` and Signal Handlers" — "a handler that calls a function that sets `errno`… can silently clobber the value the main code path was about to check."
  - §8 "Tricky Item 3: Non-Reentrant Functions" — "Many common functions are not reentrant: `printf`, `malloc`, `free`, `strtok`."

### Question 5 — `measure_start_times(struct timespec *timestamps, unsigned n)`

**Exam-style answer**
```c
int measure_start_times(struct timespec *timestamps, unsigned n) {
    int pipe_fds[2];
    pipe(pipe_fds);

    for (int i = 0; i < n; i++) {
        pid_t child_pid = fork();
        if (child_pid == 0) {
            close(pipe_fds[0]);
            struct timespec timestamp;
            if (clock_gettime(CLOCK_REALTIME, &timestamp) == -1) {
                perror("clock_gettime");
                close(pipe_fds[1]);
                exit(1);
            }
            write(pipe_fds[1], &timestamp, sizeof(struct timespec));
            close(pipe_fds[1]);
            exit(0);
        }
    }

    close(pipe_fds[1]);
    int nread = 0;
    while (read(pipe_fds[0], timestamps + nread, sizeof(struct timespec)) > 0) {
        nread++;
    }
    close(pipe_fds[0]);

    int ret_val = 0;
    int status;
    for (int i = 0; i < n; i++) {
        wait(&status);
        if (WEXITSTATUS(status) != 0) {
            ret_val = -1;
        }
    }
    return ret_val;
}
```

**Why this is correct**
A single pipe is created *before* forking so every child inherits both ends. All `n` children are forked in one loop first (satisfying "do not collect any data until all children have been started," letting them run in parallel), each closing its unused read end, timestamping itself, writing that timestamp to the shared write end, and exiting. Because `sizeof(struct timespec)` is far under `PIPE_BUF` (512-byte POSIX guarantee / 4096-byte Linux guarantee), concurrent children's writes to the one shared pipe never interleave. The parent closes its own copy of the write end *before* reading — this is what lets its read loop eventually see EOF (return 0) once every child has exited and closed its own write end, rather than blocking forever. Only `clock_gettime` gets explicit error handling, exactly as the spec requires; a child's failure is signaled through its own exit status and folded into the return value via `WEXITSTATUS`.

**Local source evidence**
- `csci4061-fa26/Lecture/lecture08-code/single_pipe.c` — the *exact* same "n children, one shared pipe, parent closes write end then reads until EOF" skeleton (there: each child writes an `int`; here: a `struct timespec`).
- `20_Progress/Degree/CSCI 4061/Weekly/Week - 4.md` §13 "Solving the Exercise: One Pipe, Then an Array of Pipes" — names `lecture08-code/single_pipe.c` directly as "this exact solution," and explains why atomicity holds: "each write (`sizeof(int)` = 4 bytes) is nowhere near `PIPE_BUF`."
- `csci4061-fa26/Labs/lab04-code/pipeline_commands.c` — same close-end-you-don't-use-before-the-real-work discipline, for the parallel `dup2`-based pattern.
