````
## Concept-note discipline
Four concept layers exist in this course now, each a real subfolder under `Concepts/`, and they are not interchangeable - routing a note to the wrong one defeats the point of having four. A concept note is never a record of what a source said (that's the Weekly or Textbook note's job); it is a record of what can be explained and applied without reopening the source, held to [[Concept Standard]]'s full bar - no bland restated-fact header, no section kept just because the template has a slot for it. If a section would only repeat the Mechanism in different words, cut it.

**`Concepts/C Refresher/`** rebuilds the CSCI 2021 prerequisite this course assumes but never re-teaches - pointers, arrays/strings, structs, dynamic memory, linked structures, recursion, file I/O, compilation/linking, bitwise/integer representation, x86-64 memory layout. Landed as ten source-grounded notes plus the [[20_Progress/Degree/CSCI 4061/Concepts/C Refresher/C Language|C Language]] hub - this is the working gold example for this course's hub-note shape and is mostly a one-time build, revisited only when lab or project work exposes a real gap in it, never on a schedule.

**`Concepts/Lecture/`** is where a genuinely cross-cutting 4061 mechanism goes once it has recurred across three or more weeks of OS material - the process lifecycle (fork/exec/wait, zombie/orphan/daemon), the fd → system-file-table → inode chain, the signal-delivery/default-disposition/blocking model. Source priority is the lecture slide PDF first, reconciled against the matching textbook chapter and the week note's own live `## Lecture` capture - never the reverse. Empty as of 2026-10-05; populating it from Weeks 1-4 is the course's main open concept-layer gap right now.

**`Concepts/Code/`** holds concept notes that originate from a lab's or project's own implementation - a pattern worth carrying forward (the fork-exec-wait skeleton from Lab 1/2's `fork_exec.c`/`fork_wait.c`, a signal-masking trap from Lab 3's `wc_signal.c`, a piece of Project 1's own architecture) rather than a lecture topic treated in the abstract. These notes cite the actual starter code and `QUESTIONS.txt` from the dev container, never a paraphrase of the assignment's prompt. Empty as of 2026-10-05 - Labs 1 and 2 and Project 1 have not yet been pulled into this layer.

**`Concepts/Exams/`** is the narrowest layer and the easiest to get wrong: a note here is never a new explanation, only the exam-depth extension of a concept that already has a home in `Lecture/`, `C Refresher/`, `Code/`, a Weekly note, or a Textbook chapter. It exists because the exam will test a distinction the source-layer note only treats in passing - it interlinks back to that source note rather than re-deriving it, and earns its place by naming specifically what's confusing (a sequencing trap in fork/exec ordering, a signal-masking edge case, an off-by-one in the fd table after `dup2`) and drilling exactly that, not the surrounding topic. [[20_Progress/Degree/CSCI 4061/Concepts/Exams/Midterm - 1 MOC|Midterm - 1 MOC]] is this layer's hub per exam - its Map section should read as connected prose that walks the exam's actual scope and links out mid-sentence to every concept note it draws from, the same shape [[20_Progress/Degree/CSCI 4061/Concepts/C Refresher/C Language|C Language]] already demonstrates, never a bare bullet list of links.

**Writing standard across all four layers:** follow [[Concept Standard]]'s per-heading requirements exactly, and on top of that, write interlinks inline, inside the sentence that needs them (" - the same **fd table** `dup2` rewrites, see [[...|fd/inode chain]] - "), not as a trailing "Related:" dump; this is what actually makes the vault's graph useful mid-read, per [[HUMAN_WRITING]]. Never pad a section to look complete - a short Contrast naming the one real confusable pair beats a long one restating the Mechanism. Flashcards test the trap, never the label, and should be written only after the actual misconception is named in Failure Modes, so the card and the note test the same pain point from two angles.
````

````
### Part 1: QUIZ, C Extensions for Python
1. **`PyArg_ParseTuple(args, "O!", &PyList_Type, ...)` — what happens if the argument isn't a valid Python list?**
	(X) **A `TypeError` will be raised by the function.** The CPython C API docs for the `O!` format code are explicit: it is like plain `O` but also takes the address of a type object (here `&PyList_Type`); "if the Python object does not have the required type, `TypeError` is raised." It is not silently converted (lists don't get auto-converted from arbitrary types) and no `NULL`/`ValueError` path exists for this format code.
2. **`PyList_New` successfully creates a new list — what's true about its reference count?**
	(X) **The reference count is currently 1. If we no longer need the list in the future, we need to call `Py_DECREF` to avoid a memory leak.** `PyList_New` is documented as returning a **new reference** — the caller already owns one reference to the list it gets back, not zero. That's exactly why `square_roots` can return `output_list` directly without an extra `Py_INCREF` (ownership transfers straight to the caller), but also why every early-exit path in this lab's implementation calls `Py_DECREF(output_list)` before returning `NULL` on error — otherwise that one owned reference leaks.
3. **Which C function indicates a failed memory allocation back to Python?**
	(X) **`PyErr_NoMemory`.** It's the documented convenience function for exactly this case — it raises `MemoryError` with no arguments needed. `PyErr_Format`/`PyErr_SetFromErrno` require arguments this situation doesn't have (a format string, or a `errno` value — malloc-style failures inside the Python allocator don't set `errno`), and `PcLoadLetter` isn't a real CPython API function.
4. **What happens to the reference count of `o` when calling `PyList_SetItem(list, i, o)`?**
	(X) **The object's reference count stays the same.** `PyList_SetItem` is documented as "stealing" a reference to the item it's given — it takes over ownership of the reference the caller already holds rather than creating a new one, so it does **not** increment the count on entry. (Contrast: `PyList_Append` does **not** steal — it increments the count itself, so a caller that also holds its own reference to the appended object must still `Py_DECREF` it separately or leak it. This lab's implementation uses `PyList_SetItem`, not `PyList_Append`, specifically so the freshly created `PyFloat_FromDouble` result's one owned reference transfers straight into the list with no separate decref needed.)
### Part 2: CODE, complete `square_root.c`

*Decision points:*
- **Parse with `"O!"` and `&PyList_Type`**, matching quiz Q1 — rejects anything that isn't actually a list with a `TypeError`, before any list operations run.
- **`Py_ssize_t len = PyList_Size(input_list);` then `PyList_New(len)` once**, up front — matches quiz Q2: the returned `output_list` already carries one owned reference, which later either transfers to the caller (success path) or gets `Py_DECREF`'d (every error path).
- **Loop with `PyList_GetItem` (borrowed reference — no decref needed) + `PyLong_AsLong`** to read each input element as a C `long`.
- **On a negative value:** `Py_DECREF(output_list)` first (quiz Q2's leak-avoidance rule), then `PyErr_SetString(PyExc_ValueError, "Cannot compute square root of negative value")` — the exact message `QUESTIONS.txt` specifies — then `return NULL`.
- **Otherwise:** `PyFloat_FromDouble(sqrt((double)value))` creates a new float (one owned reference), and `PyList_SetItem(output_list, i, result)` steals that reference straight into the list (quiz Q4) — no `Py_DECREF(result)` needed afterward, since ownership already moved.

#include <Python.h>
#include <math.h>
#include <stdio.h>

// Function definition at the end of this file
PyObject *square_roots(PyObject *self, PyObject *args);

static PyMethodDef square_root_methods[] = {
    {
        .ml_name = "square_roots",
        .ml_meth = square_roots,
        .ml_flags = METH_VARARGS,
        .ml_doc = "Compute square roots of all numbers in a list",
    },
    {
        .ml_name = NULL,
        .ml_meth = NULL,
        .ml_flags = 0,
        .ml_doc = NULL,
    }};

static struct PyModuleDef square_root_module = {
    .m_base = PyModuleDef_HEAD_INIT,
    .m_name = "square_root_numbers",
    .m_doc = "Compute square roots of all numbers in a list",
    .m_size = -1,
    .m_methods = square_root_methods,
};

PyMODINIT_FUNC PyInit_square_root(void) {
    return PyModule_Create(&square_root_module);
}

PyObject *square_roots(PyObject *self, PyObject *args) {
    PyObject *input_list;
    if (!PyArg_ParseTuple(args, "O!", &PyList_Type, &input_list)) {
        return NULL;
    }

    Py_ssize_t len = PyList_Size(input_list);
    PyObject *output_list = PyList_New(len);
    if (output_list == NULL) {
        return PyErr_NoMemory();
    }

    for (Py_ssize_t i = 0; i < len; i++) {
        PyObject *item = PyList_GetItem(input_list, i);
        long value = PyLong_AsLong(item);

        if (value < 0) {
            Py_DECREF(output_list);
            PyErr_SetString(PyExc_ValueError,
                             "Cannot compute square root of negative value");
            return NULL;
        }

        PyObject *result = PyFloat_FromDouble(sqrt((double)value));
        if (result == NULL) {
            Py_DECREF(output_list);
            return PyErr_NoMemory();
        }
        PyList_SetItem(output_list, i, result);
    }

    return output_list;
}

## Errors + fixes
### `PyList_SetItem` vs `PyList_Append` — the real trap this lab is built around
- Problem: it's easy to reach for `PyList_Append(output_list, result)` instead of `PyList_SetItem(output_list, i, result)` since `output_list` was already pre-sized with `PyList_New(len)`, and `Append` reads more naturally for "add this computed value to the list."
- Fix: use `PyList_SetItem(output_list, i, result)`, matching quiz Q4's answer, and do not call `Py_DECREF(result)` afterward.
- Why: `PyList_New(len)` pre-fills every slot with `NULL`, not empty — the list already has `len` slots to *set*, not append into (appending would double its intended length). More importantly, `PyList_SetItem` *steals* the reference to `result`, while `PyList_Append` does not — calling `Append` and then forgetting a matching `Py_DECREF(result)` would leak exactly one reference per list element, silently, on every single call. `SetItem` was chosen specifically so the `PyFloat_FromDouble` call's one owned reference transfers directly into the list with nothing left over to clean up.
- Evidence: the 100,000-iteration reference-count check above shows the input list's refcount unchanged after the loop; the same check run against an `Append`-based draft (scratch-tested, not the submitted version) showed the *output* list objects accumulating un-freed float references under `sys.getrefcount` instead of being garbage-collected after `del r`.
### A multi-line Python verification script failed through PowerShell's quoting
- Problem: running a multi-line `python3 -c "..."` edge-case/leak-check script through `docker exec` via PowerShell failed immediately with `Remove-Item on system path '"' is blocked`, before Python ever ran.
- Fix: write the verification script to a local `.py` file first, copy it into `lab06-code/` (outside the Gradescope-submitted file set), run it with `docker exec ... python3 lab06_check.py`, then delete the copy once it was no longer needed.
- Why: PowerShell's own quoting/escaping rules don't pass a long, multi-line, nested-quote Python one-liner through to a `docker exec bash -c "..."` layer cleanly — the outer PowerShell parser was interpreting part of the embedded Python string as its own token. A real file sidesteps all of that by removing the need for any inline quoting.
- Evidence: the identical script, run as a file instead of an inline `-c` string, printed the expected five lines (`empty:`, `single:`, `end-negative ok:`, `all-negative ok:`, `refcount base/after: 2 2`) with no errors.
````

````
1 long counter = 0; 2 3 void \*worker(void \*arg) {4 for (int i = 0; i < 1000000; i.+) 5 **counter++;** 6 return NULL; 7 }

## What

Two threads touch the same memory, at least one writes, and nothing orders them.

**Where** One stack trace per thread. Here both point at line 5.

**Fix** Lock around the access. Run again: no report.
````

````
### Quiz answers (6 total, 6 flipped)
1. **Third argument of `pthread_create`, `void *(*start_routine)(void *)`:** a pointer to a function taking one `void *` and returning `void *`. The leading `void *` is the return type, `(*start_routine)` is the pointer, `(void *)` is the one parameter.
2. **When the new thread starts:** immediately once `pthread_create` succeeds (slide 3: "starts running as soon as pthread_create succeeds"). `pthread_start` does not exist, and `pthread_join` only waits. "Immediately" means runnable, not that it runs before `pthread_create` returns.
3. **Second argument of `pthread_join`:** where to store the thread's return value, a `void **`. This lab passes `NULL` because `worker` returns `NULL` and the result goes through `global_sum`.
4. **TSAN's error:** a data race with the `global_sum` variable. TSAN's own wording is `WARNING: ThreadSanitizer: data race` (slide 6: two threads touch the same memory, at least one writes, nothing orders them).
5. **Initializing a global mutex:** assign `PTHREAD_MUTEX_INITIALIZER`. `PTHREAD_COND_INITIALIZER` is for condition variables. "Globals are zero-initialized" happens to work on glibc but POSIX does not promise it, and `pthread_mutex_init` at the top of `main` works but is dynamic initialization for something that can be static.
6. **Error-checking `pthread_mutex_lock`:** save the return value, test for non-zero, print with `strerror` (slide 3: pthread functions return an error number and do not set `errno`, so `perror` would print a stale `errno`).
`socrates` checks the file as one hash, so it confirms the set of six together, not each answer on its own. The reasoning above is mine; the hash only says the set is right.
### Part 1 and 2: `sum_files.c`
Decisions, in the order they came up:
- **Uncomment `file_names`** by deleting the `/*` and `*/` lines only.
- **Pass `file_names[i]` itself as the thread argument**, cast back to `const char *` in `worker`. Each string literal lives for the whole program, so no per-thread struct and no `malloc` is needed. Contrast with passing `&i` of the loop counter, which races because `i` changes before the thread reads it (the slide avoids this with an `ids[]` array).
- **Track `n_created`** so a failed `pthread_create` still joins only the threads that really exist; never join an uninitialized `pthread_t`.
- **Check `sum_file(...) == -1`** and skip the add. `sum_file` already `perror`s and returns `-1` on failure; adding it would silently shave 1 off the total. The catch is that a file whose real sum is `-1` would also be skipped, which cannot happen with these inputs.
- **Lock only around `global_sum += file_sum`.** `sum_file` runs outside the lock, which is the whole point of the threads. Holding the lock across the file read would serialize the work.
- **Every error path returns** with the lock released: if `pthread_mutex_lock` fails, `worker` returns before touching `global_sum`, so there is nothing to unlock.
- **`main` returns 1 before the provided `printf`** if any create or join failed, rather than printing a partial sum.
```c
long global_sum;
pthread_mutex_t global_sum_lock = PTHREAD_MUTEX_INITIALIZER;
// worker
const char *file_name = (const char *)arg;
long file_sum = sum_file(file_name);
if (file_sum == -1) return NULL;
int ret = pthread_mutex_lock(&global_sum_lock);
if (ret != 0) { fprintf(stderr, "pthread_mutex_lock: %s\n", strerror(ret)); return NULL; }
global_sum += file_sum;
ret = pthread_mutex_unlock(&global_sum_lock);
if (ret != 0) { fprintf(stderr, "pthread_mutex_unlock: %s\n", strerror(ret)); }
// main
pthread_t threads[N_THREADS];
for (int i = 0; i < N_THREADS; i++) { ret = pthread_create(&threads[i], NULL, worker, file_names[i]); /* check, break, n_created++ */ }

## Errors + fixes
### TSAN aborts at startup: `unexpected memory mapping`
- Problem: `make test` failed test 2. `./sum_files` printed `FATAL: ThreadSanitizer: unexpected memory mapping 0x...-0x...` and exited 66 before `main` ran. An empty `int main(void){return 0;}` compiled with `-fsanitize=thread` failed identically, so the program under test was not the cause.
- Fix: run under `setarch x86_64 -R` (disables address-space randomization for that process and its children), e.g. `setarch x86_64 -R make test`. No system setting changed.
- Why: TSAN reserves fixed shadow-memory ranges and aborts if the kernel maps something inside them. Here the kernel is `6.18.54.[REDACTED]` with `vm.mmap_rnd_bits = 32` and gcc 11.4's TSAN runtime. Turning ASLR off made the empty program run, which fits an ASLR-entropy mismatch. That is the explanation I am confident in from the evidence; I did not test the other known remedy, lowering `vm.mmap_rnd_bits` to 28 on the WSL VM.
- Evidence: empty program exit 66 without `setarch`, exit 0 with it; `setarch x86_64 -R make test` gave 2/2 and 1.0/1.0.
### The data race Part 1 is built to show
- Problem: with the lock calls removed from a scratch copy of the finished code (not the submitted file), three runs each printed `WARNING: ThreadSanitizer: data race`, with a size-8 read in thread T2 and a previous size-8 write in thread T1, both at the `global_sum += file_sum` line, location `global 'global_sum' of size 8`, and exited 66. The program still printed `Sum for all files = 19241311`, the correct total.
- Fix: add `pthread_mutex_t global_sum_lock = PTHREAD_MUTEX_INITIALIZER;` and wrap only `global_sum += file_sum` in `pthread_mutex_lock` / `pthread_mutex_unlock`.
- Why: `+=` on a global is load, add, store. Two threads can load the same old value and both store, losing one file's sum. A correct printed number only means the schedule was lucky this time. TSAN flags the missing happens-before ordering between the two accesses, not a wrong value, which is why it fails the test even when the sum matches.
- Evidence: the three lock-free reports above; the locked version gives no report in 10 runs and in `make test`.
### Reading the lock-free run on a wrong working directory
- Problem: my first lock-free experiment printed four `fopen: No such file or directory` errors and no TSAN report, which looked like "no race".
- Fix: copy `test_cases/resources/` next to the scratch binary and rerun; the race report then appeared on every run.
- Why: with every `sum_file` returning `-1`, `worker` returns before touching `global_sum`, so there is no shared access to race on. Absence of a TSAN report only means the racy code path did not execute.
- Evidence: the missing-file run printed sum 0 and no report; the run with inputs present printed the report three times out of three.

Why does `perror` give the wrong message after a failed `pthread_mutex_lock`?::`pthread_*` functions return the error number and do not set `errno`, so `perror` prints whatever stale value `errno` holds. Save the return value and print `strerror(ret)`.
Why pass `file_names[i]` to `pthread_create` instead of `&i`?::The thread reads its argument some time after `pthread_create` returns, by which point the loop has changed `i`. A pointer to a string literal (or to a per-thread slot like `ids[i]`) stays valid and unchanged.
````
