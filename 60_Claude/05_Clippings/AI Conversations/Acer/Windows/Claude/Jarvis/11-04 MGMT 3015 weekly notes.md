# Vault Lint
## Purpose
Measures how many notes fit their Standard and checks that the kit files (Standards, Templates, Workflows) agree with each other. Without it the goal of 90% fit has no number, and a Standard can drift from its Template unnoticed.
## Trigger
Run by hand: `node vault-lint.js` from this folder. Run `--kit` after any change to a Standard, Template, or Workflow. The `note-to-actions` and `transcript-to-brief` skills call it on the one folder they just wrote to. No scheduled task of its own exists. Until 2026-11-04 nothing recorded the fit percentage on a schedule: neither the `weekly-review` skill nor `run-weekly-review.ps1` called it (checked by searching the skill, `run-weekly-review.ps1`, its registration script and its launcher for `vault-lint`, `vault lint`, `fit %` and `conformance`). Now Step 7.7 of `.claude/skills/weekly-review/weekly-review.md` (and its `.agents` copy) runs `order-health.js`, pastes the block under `Vault Health` in the Weekly Synthesis note and adds one sentence on the fit change. That wiring is text in the skill, so it first takes effect on the next run (the `Jarvis-WeeklyReview` task, Sunday 2026-11-08 at 06:00) and I have not seen it produce a note yet.
## Inputs and Outputs
Reads every `.md` file under the vault root (found three folders up from the script), the Spec blocks in `30_Order/Standards/`, the vocabulary tables in [[Frontmatter Standard]], and `vault-lint.config.json`. By default it writes nothing into the vault; only `--fix` writes (see below). `--json FILE` writes a report wherever you point it, which should be an ignored or scratch folder.
Beyond front matter, headings, links, and placement, it enforces the shape of an action note from [[Action Standard]] and warns about two formatting rules from [[Jarvis Writing and Formatting]]. Failure codes read `<check>:<reason>`. Warnings list line numbers as `L12,L40`.
- Warnings `table-no-blank-above` and `dataview-no-blank-above`: a Markdown table, or a fenced `dataview` or `dataviewjs` block, starts on the line after text. A heading, a closing code fence, a callout title, or the end of an HTML comment above is allowed, and so is a blank line. Tables inside fenced code and frontmatter are ignored. The single blank line that fixes it is not counted as `extra-blank-lines`. They are warnings only: they never fail a note or change the fit percentage, so that number stays a pure structure measure. They print in a Warnings section after the report (first 20 notes, or `--list N`) and in the `--json` output under `warns`. `--fix` repairs them, and nothing else (see below).
- `7:todo-missing`, `7:todo-not-under-opening`, `7:todo-lines:N`, `7:todo-next-mismatch`, `7:checkbox-outside-todo:N`, `7:missing-subheading:<name>`: for `action` notes, a `> [!todo]` callout sits directly under the opening line, holds one to three `- [ ]` lines, the first equal to `next`, no checkbox appears outside it, and Open Threads has the subheadings the Spec names. The Spec keys are `todo_callout` and `open_threads_subheadings` in [[Action Standard]]; change the Standard, not the script.
`order-health.js` is the weekly report. `node order-health.js` runs `vault-lint.js` and `vault-lint.js --kit` with `--json` into the OS temp folder (deleted afterward), reads `30_Order/Note Type Registry.md`, and prints one Markdown block to stdout: the fit line, the kit error and warning counts, a table of families below 100% with their top three failure reasons (`--top N` changes the three), the families that have a Spec and no notes, the Standards, Templates and Workflows with no link in the Registry (files starting `00_` are skipped), and a short list of proposals. It never passes `--fix` and writes no file; whoever calls it decides where the text goes. For the weekly review that place is the `Vault Health` section of the Weekly Synthesis note, under a line `Order health`.

## Failure Behavior
It edits a note only under `--fix`: it inserts one blank line above each table or fenced `dataview`/`dataviewjs` block flagged by the two warnings, and changes nothing else. It never touches frontmatter or tables inside fenced code, keeps a file's line endings, and checks that removing blank lines from the old and new text gives identical text before it writes (a note that fails the check is skipped and reported). `--dry-run` prints the same changes and writes nothing, and wins if both flags are given. `--skip PREFIX,PREFIX` leaves path prefixes alone, for example the read-only clippings. Run `--dry-run` first. A Spec block that is not valid JSON is reported as an error, and notes of that family then fall to `unmapped`. `--kit` exits with status 1 when it finds an error, so it can gate a commit. A `maps_to` entry in a Standard resolves to a file when the link equals the file's vault-relative path without `.md`, or the file's path ends in `/` plus the link (so `[[Name]]` and `[[30_Order/Templates/AI Toolkit/Name]]` both work, and a link no longer matches a file whose name merely ends with the same letters). ## Key ideas (short)
- A file system's whole job is turning **one flat array of disk blocks** into a hierarchy, using **i-nodes** to store metadata separately from names and **directories** to supply the names.
- **Directories are files** - plain-looking (name, i-node number) pairs - so they get a dedicated read-only API (`opendir`/`readdir`) specifically so no program has to understand their internal layout to use them safely.
- A **hard link** is a second directory entry pointing at the same i-node; a **symbolic link** is an independent file holding a path string - only the second can dangle, point across file systems, or target something that doesn't exist yet.
- A **pipe** is two file descriptors sharing one kernel buffer - `close()` on either end isn't just resource cleanup, it's how a process tells the kernel (and therefore every other process sharing the pipe) "I will never read/write here again."
- **`PIPE_BUF`** is the write size under which the kernel guarantees no interleaving between concurrent writers - exceed it and bytes from different processes can genuinely interleave.

## Examples worth keeping
- **The `proj1-code`/`proj2-code` shared-inode picture** (Lec07): two directories, each with their own entry for `job_list.h`/`job_list.c`, both entries pointing at the *same* i-node numbers (`0x0004`, `0x0008`) - the lecture's clearest single image for "a hard link is just another name for the same i-node," immediately followed by the symlink version where the second directory's entries instead hold a *path string* to the originals.
- **`total_dir_size()`** (Lec07 exercise, solved live in `lecture07-code/dir_size.c`): `opendir(".")`, loop `readdir()` until `NULL`, skip anything that isn't `DT_REG`, `stat()` each regular file and sum `st_size` - the canonical shape for "do something to every file in a directory" that `openat()`/`nftw()` later generalize to arbitrary paths and recursive subdirectories.
- **The pager-via-pipe program** (Chapter 15, Fig. 15.6): streams a file into `$PAGER` through a pipe instead of a temp file - the parent's final `close(fd[1])` after the last `write()` is simultaneously cleanup *and* the EOF signal the child's pipe-read is waiting for.
- **`process_files()` with a single shared pipe** (Lec08 exercise, solved live in `lecture08-code/single_pipe.c`): `n` children each `fork()`ed off a *single* pipe, each writing one `int` result to the shared write end before exiting; the parent closes its own write end, then `read()`s in a loop until it returns 0, relying on `PIPE_BUF` atomicity (`sizeof(int)` is nowhere near 512 bytes) to guarantee no child's 4-byte write ever interleaves with another's.
- **The word-frequency pipeline** (Lec08, recapping Lec04): `tr -cs A-Za-z '\n' | tr A-Z a-z | sort | uniq -c | sort -rn | head -n 10` - six small, sharply focused tools chained through five pipes, the lecture's running example for "the Unix philosophy."
## Lecture
### 1. Building a File System on Raw Blocks (Lec07, 9/29)
A file system has exactly three jobs on top of "an array of data blocks": track which (possibly scattered) blocks belong to each file, track which blocks are free (one bit per block - a free map), and build the directory hierarchy that maps human-readable names to that bookkeeping information. **I-nodes** solve the first and third problems together: a fixed-length record per file storing size, permissions, owner/group, and - organized as a tree of direct pointers, then single/double/triple indirect pointers as a file grows - the actual disk-block indexes holding its contents. An i-node conspicuously does **not** store the file's name; `stat()`/`fstat()` (`int stat(char *path, struct stat *statbuf); int fstat(int fd, struct stat *statbuf);`, 0 on success, -1 with `errno` set) are how a program actually reads that metadata into a `struct stat` it provides.
### 2. Why Fixed-Size Blocks, I-node Numbers, and the `ls -li` Picture (Lec07, 9/29)
Fixed-size-block allocation means growing or shrinking a file is just allocating or freeing blocks - no need to find one contiguous region of exactly the right size - at the cost of more bookkeeping to track which scattered blocks belong to which file. Every i-node gets a number giving its position in the i-node array; that number *is* effectively the disk block number for its metadata, visible directly via `ls -li` (the lecture's own real example: `25153730 -rw------- 1 jhkolb … file_list.c`, matching the same file permissions Week 2 already examined from a different angle). The number of bits used for i-node numbers caps the maximum number of files a file system can ever hold.
### 3. Directories and Path Resolution, Recap and Confirmation (Lec07, 9/29)
A directory is nothing more than a special kind of file whose contents are a list of (name, i-node number) entries - confirming exactly the picture [[20_Progress/Degree/CSCI 4061/Weekly/Week - 3|Week 3]] already built from Lec06's early preview. Lec07 re-walks `open("/home/sun/hello.txt")` i-node lookup by i-node lookup (root's known i-node → find `home`'s entry → find `sun`'s entry → find `hello.txt`'s entry) as direct confirmation, not new material - see Week 3's own Worked Example for the full step-by-step. **Directory permissions** get their own precise reading here: read lets you list entries, write lets you add/remove entries, execute lets you traverse through the directory as a path component - `x` alone means you can open a file inside it *if you already know the name*, but can't `ls` it.
### 4. The Buffer Cache, Confirmed from the OS Side (Lec07, 9/29)
A four-stage picture of what `read()`/`write()` actually touch: (1) a file is opened, its i-node copied into an i-node table entry; (2) `read()` completes by pulling from the **buffer cache** - a chunk of kernel-controlled main memory holding recently read/written blocks, not the disk directly; (3) `write()` completes by updating the buffer cache, not disk; (4) the OS eventually flushes dirty buffers to disk, either via an explicit `fsync()` call or automatically roughly every 15 seconds. This is the same buffering idea Week 2 covered from the stdio/kernel-write split; here it's one layer lower, inside the kernel's own disk-block caching.
### 5. The Directory API and the `total_dir_size()` Exercise (Lec07, 9/29)
Directories could technically be edited with plain `open`/`read`/`write`/`close`, but a dedicated API exists specifically so a systems programmer never has to understand a directory's actual on-disk layout to use one safely: `DIR *opendir(char *dirname);`, `struct dirent *readdir(DIR *dirp);` (repeat calls, `NULL` on end-of-directory or error, much like `strtok()`), `int closedir(DIR *dirp);`, `void rewinddir(DIR *dirp);`. There is deliberately no `writedir()` - directories are modified by adding or removing actual files, never by writing directory-entry bytes directly. The live exercise - compute the total byte size of every regular file in the current directory - is solved in full in `lecture07-code/dir_size.c`: `opendir(".")`, loop `readdir()` until `NULL`, check `d_type == DT_REG` to skip subdirectories and symlinks, `stat()` each matching entry and sum `st_size`. Generalizing to an arbitrary path needs `strcat`/`openat()` to build each file's full path (trivial in Python/Java, genuinely more work in C); generalizing to recurse into subdirectories has a ready-made library answer, `nftw()` ("file tree walk"), rather than hand-rolled recursion.

## Chapter 1: The Power of Entrepreneurship

*Context:* Chapter 1 opening introduces the global impact of new ventures, opening with Airbnb founders Nathan Blecharczyk, Brian Chesky, and Joe Gebbia (p. 1-2). *Schumpeterian Foundation:* Moravian-born economist Joseph Schumpeter (writing in Vienna in the early 20th century) defined an entrepreneur as ==a person who destroys the existing economic order by introducing new products and services, by introducing new methods of production, by creating new forms of organization, or by exploiting new raw materials== (p. 2). Schumpeter explained that economic growth and rising living standards stem from entrepreneurial innovation. Following the Industrial Revolution in England (~1760), standard of living jumped sevenfold across 16 industrialized nations between 1870 and 1979 (p. 2). Schumpeterian "gales of creative destruction" disrupt established markets
