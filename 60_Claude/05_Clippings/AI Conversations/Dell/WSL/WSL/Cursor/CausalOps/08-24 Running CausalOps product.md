## Step 4 — Capture an in-depth timing log

There is **no built-in per-phase timer** in the codebase yet. Use these layers:

### 4a. Docker logs (best for backend phase boundaries)

In a separate terminal:

```bash
docker compose logs -f api worker 2>&1 | tee /tmp/causalops-docker-$(date +%Y%m%d-%H%M%S).log
```

Look for lines like `Gathered N child tasks`, phase changes, LLM calls, barrier waits.

### 4b. SSE events (best for UI-visible phase timeline)

Each event has a `ts` (ms) and `phase` field. Phases include `ORCHESTRATOR`, `CHILDREN_GATHER`, `EVALUATE`, `CAUSAL_SYNTH`, `COMPLETE`, `ERROR`.

After the run, diff consecutive `ts` values in your events log to get per-phase durations.

### 4c. Poll run status (coordinator phase in SQLite)

```bash
watch -n 5 "curl -s http://localhost:8000/run/${RUN_ID} | python3 -m json.tool"
```

The `phase` field tracks coordinator state: `memory_retrieve` → `orchestrator` / `standard_swarm` → `children` → `evaluator_fast` / `evaluator` → `causal_fast` / `causal_synthesis` → `reasoner` → `policy_learning` (deep only) → `memory_write` → `completed`.

### 4d. SQLite run store (post-run inspection)

```bash
sqlite3 /home/anant_gupta/projects/hub/CausalOps/data/runs.db \
  "SELECT run_id, status, phase, execution_mode, created_at, updated_at FROM runs ORDER BY created_at DESC LIMIT 5;"
```

`updated_at - created_at` gives total coordinator time per run.

### 4e. Zero-token smoke (evidence pipeline only)

Does **not** exercise the agent swarm:

```bash
curl -s http://localhost:8000/demo/estimate | python3 -m json.tool
```

Use this to confirm the stack is healthy before spending LLM tokens.

## Errors that actually happened

1. **Child LLM never works (this is the product-quality blocker)**  
   Agents use `llm.with_structured_output(...)`. NVIDIA NIM rejects `guided_json` (HTTP 400). Gemini 2.5-flash is 404 for new users. Run completed anyway with `[UNAVAILABLE - Unexpected error: …]` memos and local ranking. ATE still came from the **demo SIEM fixture**, not the scenario.

2. **Spawn concurrency is a lie when the Kafka batch is size 1**  
   Worker does `getmany(timeout_ms=500)` then `asyncio.gather` with `CAUSALOPS_SPAWN_CONCURRENCY=3`. If the second `RUN_CHILD` is not in that 500ms window, child 2 waits behind child 1. Run 2: **285s serial**. Run 3: both in one batch → parallel. Compose already sets concurrency=3; the poll window is the bug.

3. **Supabase host does not resolve** (`glbmdbwqmuttykhicasq.supabase.co` → `Name or service not known` from host and from the api container). Memory retrieve/write fail every run; coordinator swallows it as designed. Embeddings to Gemini still succeed.

4. **`langchain_nvidia_ai_endpoints` missing in `.venv`**. Host pytest collection blows up on `tests/memory/test_end_to_end.py` whenever `NVIDIA_API_KEY` is set. Docker image has the package.

5. LLM factory warnings: `chat_template_kwargs` and `reasoning_budget` are not ChatNVIDIA default params (dumped into `model_kwargs`).

I appended `GEMINI_MODEL=gemini-3.6-flash` to `.env` and recreated api/worker so NVIDIA chat would load. Chat still goes NVIDIA first when that key is set — Gemini is only embeddings + chat fallback.
